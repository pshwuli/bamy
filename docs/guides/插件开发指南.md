# 插件开发指南

> 本文档教如何从零写一个 BAMY 插件并让它跑起来：目录怎么摆、元信息怎么写、钩子怎么挂、设置怎么声明、作用域怎么选、怎么调试、怎么发布。
> 规则本身见《插件规范》，本文档只讲怎么用这些规则。
> 本文档是完整设计，不是第一版，是最终态。

---

## 一、适用场景

需要扩展框架自身的行为时读本文档。包括：

- 新写一个插件
- 给已有插件加钩子、加设置项
- 调试插件为什么加载不起来、为什么没生效
- 发布插件到插件市场

### 1.1 什么时候该写插件

一个能力如果不属于任何具体策略，而是横跨多个策略、多个实例，它就该是插件。三类典型场景：

| 场景 | 例子 |
|---|---|
| 横切关注点 | 通知推送、报表汇总、审计外发，每个策略都需要但都不该各自实现 |
| 管理员管控 | 系统级规则必须由管理员一次配置、全系统生效，不能依赖用户自觉 |
| 策略不该知道的事 | 策略只表达"要买"，这笔单子要不要被拒、要不要改小属于框架侧决策 |

### 1.2 什么时候不该写插件

- 这是交易决策逻辑：什么时候开、开多少、什么条件平。这是**策略**的事，见《策略开发指南》。
- 这只是某个策略的私有计算：放进该策略自己的 `helpers/`。
- 这需要下单、平仓、撤单：框架不向插件提供任何下单接口，这类需求只能由策略实现。
- 这只是想改一个参数默认值：改实例参数即可，不需要插件。
- 这需要读取策略的内部状态：插件拿不到，策略与插件互不可见。

## 二、前置条件

### 2.1 环境

| 项 | 要求 |
|---|---|
| 运行环境 | Python 3.11 及以上 |
| 框架 | BAMY 已在本机可运行 |
| 目录 | 已存在 `extensions/plugins/` 目录 |
| 依赖 | 插件自带的第三方库写进 `requirements.txt`，或在 `dependencies.packages` 里声明 |
| 权限 | 要建全局绑定需管理员身份；要建用户级、账号级绑定需用户身份 |

### 2.2 心智准备

四条必须先接受的规则：

1. **插件不能下单。** 框架不向插件提供任何下单、平仓、撤单接口，这是最硬的一条边界。
2. 插件不能直接碰数据库、文件系统与环境变量，框架沙箱会拦截。沙箱只防误操作，不防恶意代码；插件与框架同进程运行，只安装可信来源的插件包。
3. 插件只在声明了 `network` 且限定 `hosts` 白名单的前提下可以出网。
4. 插件按绑定运行，不按插件运行。同一插件挂三个作用域，就有三个互相独立的插件对象与三份设置。

违反这些规则的写法，插件无法加载或运行即报错。这不是限制，是让插件在实盘、模拟盘、多账号环境下都能被框架统一管理的前提。

## 三、五步做出第一个插件

本节以 Telegram通知插件为例走一遍最短路径。示例只给结构，具体实现由插件作者完成。

### 3.1 第一步：建目录

```text
extensions/plugins/
  my_plugin/
    plugin.yaml
    plugin.py
    __init__.py
```

目录名就是插件 ID，规则：

- 只允许小写字母、数字、下划线
- 长度 3-32 字符
- 全局唯一（与策略 ID 不在同一命名空间，允许同名，但不建议）
- 不能以 `__` 开头

### 3.2 第二步：写 plugin.yaml

种类与元信息：

```yaml
kind: plugin
id: telegram_notify
name: Telegram通知
version: 1.0.0
author: 作者名
description: 把系统事件推送到 Telegram
tags: [notify]
min_bamy_version: 1.0.0
```

作用域、数据范围、优先级：

```yaml
scopes: [global, user, account]
default_scope: account
data_scope: own
priority: 100
```

钩子：

```yaml
hooks:
  - event: system.alert
    handler: on_alert

  - checkpoint: order.before_submit
    handler: before_order
    fail_mode: open
    timeout_ms: 200
```

`kind` 必须为 `plugin`，框架靠它区分插件包与策略包。`hooks` 至少声明一个，`scopes` 至少声明一个。

### 3.3 第三步：写 plugin.py

```python
from bamy.plugin import BasePlugin, PluginContext, ALLOW, DENY, MODIFY


class TelegramNotify(BasePlugin):
    async def on_bind(self):
        """绑定生效时调用一次。"""

    async def on_settings(self):
        """该绑定的设置被修改时调用。"""

    async def on_unbind(self):
        """绑定被删除或停用时调用一次。"""

    async def on_alert(self, event):
        """订阅型钩子：只接收，不改变流程。"""

    async def before_order(self, payload):
        """拦截型钩子：必须返回 ALLOW / DENY / MODIFY 之一。"""
        return ALLOW


PLUGIN = TelegramNotify
```

要点：

- 类名随意，但必须继承 `BasePlugin`
- 必须导出模块级变量 `PLUGIN`
- `on_bind` 与 `on_unbind` 必须有
- 所有方法与钩子处理函数都是 `async`
- 钩子处理函数的名字必须与 `plugin.yaml` 里 `handler` 字段完全一致

### 3.4 第四步：写 __init__.py

```python
from .plugin import PLUGIN

__all__ = ["PLUGIN"]
```

### 3.5 第五步：加载并试跑

1. 在管理员界面触发一次"重新扫描扩展"。
2. 确认插件出现在插件列表中，状态为已加载。
3. 建一个绑定：管理员建全局绑定，用户建用户级或账号级绑定，填好设置项。
4. 触发一次该插件订阅的事件（如让一个实例自动停止），观察日志与通知是否到达。
5. 查绑定详情页的健康度，确认调用次数增长、异常次数为零。

新扫描到的插件不会自动产生绑定，绑定必须由管理员或用户手动创建。

## 四、钩子怎么写

钩子是插件接入框架的唯一入口，分两类，先选类型再写函数。

### 4.1 两类钩子的区别

| | 订阅型（`event:`） | 拦截型（`checkpoint:`） |
|---|---|---|
| 能否否决 | 否 | 能 |
| 能否改数据 | 否 | 能 |
| 执行时机 | 事件发布后异步分发 | 流程的检查点上同步执行 |
| 是否阻塞主流程 | 否 | 是 |
| 出错影响 | 只记日志，不影响发布者与其他订阅者 | 按 `fail_mode` |
| 处理函数签名 | `async def handler(self, event)` | `async def handler(self, payload)` |
| 返回值 | 忽略 | 必须三选一 |

### 4.2 怎么选

- 插件只想"知道发生了什么"，不干预流程：用订阅型。
- 插件需要否决或改写一笔单子、一次启动、一次平仓、一批参数：用拦截型。
- 拿不准时先用订阅型。拦截型挂在关键路径上，写不好会拖慢下单或拦死交易。

### 4.3 订阅型钩子的写法

```yaml
hooks:
  - event: system.alert
    handler: on_alert

  - event: order.filled
    handler: on_filled

  - event: tick
    handler: on_tick
    throttle: 5
```

```python
async def on_alert(self, event):
    """event 是事件对象，字段按事件类型而定。"""
    # 处理逻辑
```

规则：

- 事件名只能用事件总线的既有清单，不能自造。
- 处理函数无返回值，返回值被忽略。
- 单个插件最多订阅 16 个事件。
- `tick` 是高频率事件，订阅它必须声明 `throttle`（单位秒），否则加载失败。
- 一个插件的处理函数抛异常不影响其他订阅者，但会计入健康度。

### 4.4 拦截型钩子的写法

```yaml
hooks:
  - checkpoint: order.before_submit
    handler: before_order
    fail_mode: open
    timeout_ms: 200
```

```python
async def before_order(self, payload):
    # 检查 payload，决定怎么办
    return ALLOW
```

规则：

- 必须返回 `ALLOW`、`DENY(reason)`、`MODIFY(payload)` 三者之一，返回其他值按 `PLUGIN_ERROR` 处理。
- 必须声明 `fail_mode`，不写时用默认值 `open` 并记警告。
- 必须在自己的超时内返回，默认 200 毫秒，上限 2000 毫秒。
- 处理函数里不能有阻塞操作，任何阻塞都会拖慢下单链路。
- 单个插件最多声明 32 个钩子，单个检查点上最多 16 个拦截型钩子。

### 4.5 三种返回值怎么用

| 返回值 | 用在什么场合 | 注意 |
|---|---|---|
| `ALLOW` | 检查通过，按原样继续 | 最常用，条件不满足时也应倾向放行 |
| `DENY(reason)` | 明确违规，必须拦下 | `reason` 会返回给调用方并记审计，要写清可读的原因 |
| `MODIFY(payload)` | 只需调整数量、价格、委托类型或参数值 | 只改允许改写的字段，其余原样带回 |

`MODIFY` 之后的 payload 会传给链上后续插件与框架，所以改写要保守：只动自己负责的字段。

## 五、检查点详解

### 5.1 四个检查点

只有四个检查点，不能自造新的。

| 检查点 | 时机 |
|---|---|
| `instance.before_start` | 实例启动前置校验通过后、`on_start()` 之前 |
| `order.before_submit` | 订单前置校验通过后、发出请求前 |
| `position.before_close` | 平仓动作发出前 |
| `params.before_save` | 实例参数保存前 |

顺序固定：**风控先于插件**。风控拒绝的单子不会再到插件，插件的错误也不影响风控判断。

### 5.2 各检查点的输入与可改写范围

| 检查点 | 输入 payload | 可改写字段 | 典型用途 |
|---|---|---|---|
| `instance.before_start` | `{instance, account, strategy_meta}` | 无，只能放行或拒绝 | 拒绝启动 |
| `order.before_submit` | `{instance, order, symbol, side, amount, price, type}` | `amount`、`price`、`type` | 拒单、改数量或价格 |
| `position.before_close` | `{instance, position_id, symbol, amount, is_manual}` | `amount` | 拒绝平仓、部分平仓 |
| `params.before_save` | `{instance, params}` | `params` 内的值 | 拒绝或修正参数 |

`instance.before_start` 与 `position.before_close` 不支持改写，返回 `MODIFY` 无效。

### 5.3 拒绝之后发生什么

| 检查点 | 拒绝后的表现 |
|---|---|
| `instance.before_start` | 实例不启动，状态置 `error`，`last_error` 写明被哪个插件拒绝 |
| `order.before_submit` | 下单不发出，订单记为 `rejected`，来源标记为插件拦截 |
| `position.before_close` | 平仓不执行，拒绝原因返回给调用方 |
| `params.before_save` | 参数不落库，拒绝原因返回给用户 |

拒绝产生统一错误码 `PLUGIN_DENIED`，并附 `reason` 与 `plugin_id`；插件超时导致拒绝是 `PLUGIN_TIMEOUT`，插件抛异常导致拒绝是 `PLUGIN_ERROR`。

### 5.4 拦截链的顺序

同一检查点上的多个插件按 `priority` 串行执行，数值小者先执行。任一插件返回 `DENY`，链条立即终止，后续插件不再执行。`MODIFY` 后的 payload 传给下一个插件，链上后续插件看到的是最新值。

顺序在每次执行时重新计算。插件不要假设自己在链上的位置，也不要假设链上只有自己。

### 5.5 写拦截钩子的三条实用建议

- 只拦自己真正负责的规则：一个通知插件没有理由拒绝订单。
- 拒绝时把 `reason` 写清，用户看到的就是这句话。
- 拿不准就返回 `ALLOW`，把判断留给风控和策略。

## 六、设置怎么写

### 6.1 与策略参数同一套类型系统

设置（settings）与策略的参数（params）使用完全相同的类型系统与字段定义，见《策略规范》第四、第五节。类型清单如下：

| type | 前端渲染 | 后端校验 |
|---|---|---|
| `int` | 数字框（整数） | 整数、`min`/`max` |
| `float` | 数字框（小数） | 数字、`min`/`max` |
| `string` | 文本框 | 长度、`pattern` |
| `text` | 多行文本框 | 长度 |
| `bool` | 开关 | 布尔 |
| `select` | 下拉框 | 值在 `options` 内 |
| `multiselect` | 多选框 | 值都在 `options` 内 |
| `secret` | 密码框 | 长度、存储加密 |
| `symbol` | 交易对选择器 | 合法的交易对 |
| `date` / `time` / `datetime` | 日期、时间、日期时间选择器 | 合法值 |
| `duration` | 时长选择器 | 合法时长（秒/分/时） |
| `percent` | 百分比输入 | 0-100 |

写了框架不认识的 `type` 时，加载记警告、该设置项被跳过，整个插件不会因此加载失败。

### 6.2 声明与读取

```yaml
settings:
  - key: bot_token
    label: Bot Token
    type: secret
    required: true
    help: 从 BotFather 获取
    group: 凭据

  - key: chat_id
    label: 会话 ID
    type: string
    required: true
    group: 凭据
```

```python
token = self.ctx.settings["bot_token"]
chat = self.ctx.settings["chat_id"]
```

### 6.3 secret 类型的用法

- 凭据、密钥、Token、Webhook 地址这类值一律用 `type: secret`，界面渲染为密码框。
- `secret` 字段的存储加密由框架负责，插件不需要也不应该在代码里再做加密。
- 插件设置里的 `secret` 字段只在本插件内可见，其他插件、事件对象、日志里都不会出现明文。
- 不要在日志里打印 `secret` 字段的值，日志会被审计保留。
- 键名不要只叫 `secret` 或 `key`，用 `bot_token`、`webhook_url` 这类能自述用途的名字，界面与审计里才好辨认。

### 6.4 同一插件不同绑定的设置互相独立

用户级与账号级绑定的设置由用户填写，全局绑定的设置由管理员填写。同一插件挂三级作用域，就有三份互不相干的设置值。插件不要去读"别的绑定上的设置"，框架不提供这个入口。

## 七、作用域怎么选

### 7.1 三级作用域

| 作用域 | 英文 | 谁能创建绑定 | 影响范围 |
|---|---|---|---|
| 全局 | `global` | 仅管理员 | 全系统所有账号与实例 |
| 用户 | `user` | 用户自己 | 该用户名下全部账号与实例 |
| 账号 | `account` | 用户自己 | 指定一个账号及其下全部实例 |

不设实例级作用域。要按实例做精细控制，用策略参数或账号级绑定。

### 7.2 在 plugin.yaml 里声明

```yaml
scopes: [global, user, account]
default_scope: account
allow_multiple: false
```

- 未声明的作用域，对应绑定入口不显示。
- `default_scope` 必须在 `scopes` 内。
- `allow_multiple` 控制同一作用域是否允许多份绑定，默认 `false`。

### 7.3 生效链

```text
实例 → 取该实例绑定的账号 → 收集 account 级绑定
                          → 收集该账号归属用户的 user 级绑定
                          → 收集 global 级绑定
   → 按插件去重：同一插件只生效一次，取优先级最高的一份配置
   → 优先级：account > user > global
```

### 7.4 同一插件在多级都绑定时哪份生效

- **按插件去重，不按绑定去重。** 同一插件同时在账号级与全局级有绑定时，只生效账号级那份，全局那份的设置与 `priority` 都不参与。
- **不同插件各自生效。** 多份绑定互不排斥，链上不会因为某个插件已在账号级生效就把别的插件排除掉。
- 去重后每个生效插件携带一个 `effective_scope`，审计里记录是"哪一级"生效的。
- 停用一个绑定不删除配置，`enabled` 置否即立即生效。停用全局绑定会同时影响所有未被更高级绑定覆盖的账号。

### 7.5 优先级怎么算

- `priority` 只在**同一检查点上多个不同插件**之间比较，数值小者先执行。
- 数值相同时，按 `account > user > global` 排序，仍相同则绑定创建时间早者先执行。
- `plugin.yaml` 里的 `priority` 是新建绑定的默认值，绑定上的值可以单独改。

## 八、数据范围

### 8.1 own 与 all 的区别

| 值 | 含义 | 谁能安装 |
|---|---|---|
| `own` | 只看到自己绑定所在作用域内的数据 | 管理员与用户 |
| `all` | 看到全系统的数据 | 仅管理员，插件市场里显著标注 |

- 声明 `own` 的插件：账号级绑定时只收到该账号的事件，用户级绑定时只收到该用户的事件，全局绑定时只收到系统级事件。
- 声明 `all` 的插件：无论挂在哪一级，都能收到全系统事件。
- 声明 `all` 的插件用户不可安装，只能由管理员建全局绑定。

能用 `own` 就不要用 `all`。插件只是因为"实现起来方便"而要求全系统数据，是把风险面白白放大。

### 8.2 数据怎么裁剪

事件分发前按绑定的生效作用域裁剪：

```text
事件带 (owner_id, account_id, instance_id)
  → data_scope 为 own：
      账号级绑定 → 只发 account_id 匹配的事件
      用户级绑定 → 只发 owner_id 匹配的事件
      全局绑定 → 只发 owner_id 为空的系统事件
  → data_scope 为 all：
      不裁剪，全发
```

裁剪由框架完成，插件不需要自己判断"这条事件该不该处理"。插件不要假定"没收到的事件就是不存在"，`own` 范围下没收到的事件可能发生在别的账号上。

### 8.3 敏感字段怎么脱敏

| 字段 | 处理 |
|---|---|
| 账号密钥 | 从不出现 |
| 账号的 key 明文 | 从不出现 |
| 用户密码 | 从不出现 |
| 插件设置里的 `secret` 字段 | 只在本插件内可见，其他插件不可见 |
| 其他用户的用户名 | 只在 `data_scope` 为 `all` 时可见 |

框架不提供读取账号密钥、其他插件状态、策略私有状态的方法。手段上杜绝，不靠约定。

### 8.4 状态存哪里

用 `ctx.state` 存**绑定级**键值对，不是实例级：

```python
await self.ctx.state.set("last_notify_at", ts)
last = await self.ctx.state.get("last_notify_at")
```

同一插件的不同绑定各自独立存储，不要用类属性存跨调用的状态，类属性会被同一插件的多个绑定共享。

## 九、出网

### 9.1 为什么插件是唯一能出网的扩展类型

策略一律禁止出网。通知、报表、审计外发这类动作必然要访问外部服务，框架把这唯一的出口留给插件，代价是插件必须把访问目标写进声明、接受白名单约束。

### 9.2 怎么声明 hosts 白名单

```yaml
network:
  enabled: true
  hosts:
    - api.telegram.org
  timeout_ms: 5000
```

- 不声明 `network` 时，插件的网络请求被运行时拦截并抛异常。
- 声明 `enabled: true` 但 `hosts` 为空，插件加载失败。
- 只能访问 `hosts` 里的主机，其他一律拒绝。
- 出网必须走框架提供的 HTTP 客户端，指向白名单内的地址。

### 9.3 为什么不建议随便出网

- 出网把系统内部的交易数据送到了外部服务，数据一旦离开就无法收回。
- 白名单越长，可被利用的面越大。管理员在安装前要审阅 `hosts` 列表。
- 出网慢或超时会拖住调用它的钩子；拦截型钩子上出网会直接拖慢下单。
- 声明 `all` 数据范围又出网的插件，风险叠加，应尽量避免。

### 9.4 出网失败怎么处理

- 出网失败按所在钩子的异常语义处理：订阅型钩子失败只记日志与计数，拦截型钩子失败按 `fail_mode`。
- 出网失败不影响主流程。通知发不出去不该让交易停下来。
- 有重试需求时在自己的状态里记退避时间，用 `ctx.state` 保存，不要用紧凑的忙等循环。
- 频繁的出网失败会计入健康度，累计到阈值会触发绑定自动停用。

### 9.5 出网的三条写法建议

- 拦截型钩子里不要出网。真要在下单链路上做外部校验，也应改为订阅型异步记录。
- `hosts` 写具体主机，不要用通配或宽泛的域名。
- 给外部服务设本地限频，用设置项暴露给用户，避免被外部服务封禁。

## 十、失败语义

### 10.1 fail_mode 的 open 与 closed

| 值 | 插件自身异常时 | 适用 |
|---|---|---|
| `open`（默认） | 放行，记日志与告警 | 通知类、统计类、非强制的业务规则 |
| `closed` | 拒绝，记审计 | 强制合规类、资金安全类 |

默认是 `open`，理由是：一个坏掉的插件不应该让全系统下不了单。

### 10.2 怎么选

- 插件坏了只是"少一条通知"，选 `open`。
- 插件坏了意味着"一笔不合规单子会被放过去"，选 `closed`。
- 选 `closed` 前先确认插件不会因为外部服务波动而频繁抛异常，否则会把整条下单链路拦死。
- 一个插件里不同检查点可以有不同的 `fail_mode`，按各检查点的实际风险分别选。

### 10.3 选错了会有什么后果

| 选错方向 | 后果 |
|---|---|
| 该 `open` 却选了 `closed` | 插件一抖动，下单、启动、平仓、保存参数全被拒；用户会看到大量 `PLUGIN_ERROR` 与 `PLUGIN_TIMEOUT` |
| 该 `closed` 却选了 `open` | 插件失效期间不合规的操作被静默放行，事后只能从日志与审计里追溯 |

### 10.4 健康度与自动停用

框架按插件统计：

| 指标 | 说明 |
|---|---|
| 调用次数 | 订阅型与拦截型分别统计 |
| 异常次数 | 抛错与超时之和 |
| 平均耗时 | 拦截型的关键指标 |
| 最近错误 | 最近一次错误的原文与时间 |

连续异常超过阈值（默认 10 次）时：绑定自动置为 `disabled`，发布 `system.alert` 事件，记审计，管理员后台显示为"已自动停用"并提供手动恢复按钮。

### 10.5 失败隔离

- 一个插件失败不影响其他插件。
- 插件失败不影响策略的运行。
- 插件失败不影响事件总线上其他订阅者。
- 插件卸载不需要停止实例。

## 十一、调试与排错

### 11.1 常用手段

| 手段 | 用途 |
|---|---|
| `ctx.log_info` / `log_warn` / `log_error` | 在日志里留下痕迹 |
| 绑定详情页的健康度 | 看调用次数、异常次数、平均耗时 |
| `ctx.notify(title, body, level)` | 往通知中心发一条系统通知，验证链路是否通 |
| 用模拟盘实例触发事件 | 不产生真实下单，验证订阅型钩子 |
| 手动停用再启用绑定 | 确认生效链与设置变更是否即时生效 |

### 11.2 加载失败的常见原因

| 现象 | 原因 |
|---|---|
| 插件不在列表里 | 目录以 `__` 开头，或目录名不符合命名规则 |
| 提示缺少必须文件 | 少了 `plugin.yaml`、`plugin.py` 或 `__init__.py` |
| 提示未导出 PLUGIN | `__init__.py` 没有导出 `PLUGIN` |
| 提示钩子处理函数不存在 | `handler` 名字与代码中的方法名不一致，或方法不是 `async` |
| 提示订阅 tick 未声明 throttle | `tick` 必须限频 |
| 提示出网声明不完整 | `enabled: true` 但 `hosts` 为空 |
| 提示检查点插件过多 | 该检查点上的拦截型钩子超过上限 |
| 提示作用域非法 | `scopes` 为空或含未知值，或 `default_scope` 不在 `scopes` 内 |
| 提示 kind 不对 | `plugin.yaml` 里 `kind` 缺失或不是 `plugin` |

### 11.3 运行时的常见问题

| 现象 | 原因 |
|---|---|
| 绑定建了但钩子不触发 | 绑定未启用、插件未加载成功，或被更高级作用域的同插件绑定覆盖 |
| 收到的数据比预期少 | `data_scope` 为 `own`，事件已按生效作用域裁剪 |
| 下单被自己的插件拦了 | 拦截钩子返回了 `DENY`，或改写 `amount` 时越过了风控限额 |
| 下单链路变慢 | 拦截型钩子里有阻塞操作或出网，超出了自己的超时 |
| 通知偶发收不到 | 出网失败或外部服务限频，看健康度里的最近错误 |
| 绑定被自动停用 | 连续异常超过阈值，修好插件后由管理员手动恢复，恢复后计数归零 |
| 重启后插件行为异常 | 跨调用状态存了类属性而不是 `ctx.state` |
| 改了设置没生效 | 确认改的是当前生效那一级的绑定，而非被覆盖的低优先级绑定 |

### 11.4 热更新的限制

- 插件代码被重新加载时，已生效的绑定不会自动换用新代码。
- 只保证"下次绑定解析时用新代码"，需要人工停用再启用绑定才会重新解析。
- 新代码加载失败时，框架保留旧版本继续运行。
- 插件新增依赖后需要重启服务。
- `settings` schema 有破坏性变更时，已有绑定需人工确认。

## 十二、发布

### 12.1 版本规则

- 用语义化版本：不兼容变更升主版本，新增功能升次版本，修 bug 升补丁。
- 主版本变更须在说明里写清不兼容点，尤其是 `settings` 的字段删改。
- 声明 `min_bamy_version`，避免在不支持该插件的框架上运行。
- 绑定会记录创建时的插件版本，插件升级不自动改变已有绑定的行为。

### 12.2 发布内容

| 文件 | 必须 |
|---|---|
| `plugin.yaml` | 是 |
| `plugin.py` | 是 |
| `__init__.py` | 是 |
| `requirements.txt` | 有第三方依赖时 |
| `README.md` | 是，说明用途、设置项含义、出网目标与风险 |

发布方式：直接拷贝文件夹到 `extensions/plugins/`，通过后台的上传接口上传 zip，或从 Git 仓库拉取。发布后由管理员手动触发"重新扫描扩展"。

### 12.3 兼容性检查

发布前逐项确认：

1. `kind`、`id`、`version`、`scopes`、`data_scope` 都已声明且合法
2. 声明了哪些作用域就真正支持哪些作用域，`default_scope` 在 `scopes` 内
3. 每个 `handler` 都有同名 `async` 方法
4. 拦截型钩子都声明了 `fail_mode`，并核对过选错方向的后果
5. 拦截型钩子在超时内返回，内部没有阻塞操作与出网
6. 订阅 `tick` 时声明了 `throttle`
7. 出网只访问 `hosts` 白名单内的主机，`hosts` 写得尽量具体
8. `secret` 类型的字段没有出现在日志里
9. 不调用任何下单、平仓、撤单接口
10. 在模拟盘实例上跑通绑定、钩子触发、设置变更、解除绑定
11. 连续运行一段时间，健康度里的异常次数保持为零
12. `README.md` 里写清了用途、设置项含义、出网目标与风险

## 十三、常见问题

| 问题 | 回答 |
|---|---|
| 插件能下单吗 | 不能，框架不提供任何下单、平仓、撤单接口，需要交易的能力必须由策略实现 |
| 插件能改策略的代码或状态吗 | 不能，插件只能通过检查点改写传给它的 payload，看不到策略的私有状态 |
| 插件能读另一个插件的设置吗 | 不能，同一插件不同绑定的状态互相独立，跨插件更不可见 |
| 插件能感知自己挂了哪些作用域吗 | 只能知道当前生效的那一份：`ctx.scope` 与 `ctx.scope_id` 是生效作用域，其余绑定不可见 |
| 同一插件挂三级作用域，哪份生效 | 按插件去重，`account > user > global`，只有最高那一级生效，见第七节 |
| 插件能挂在单个实例上吗 | 不能，不设实例级作用域，实例级精细控制由账号级绑定或策略参数完成 |
| 订阅型钩子能拒绝事件吗 | 不能，订阅型只接收不改变流程，要拒绝必须用拦截型 |
| 拦截型钩子返回什么 | `ALLOW`、`DENY(reason)`、`MODIFY(payload)` 三选一，返回其他值按错误处理 |
| 插件能出网吗 | 能在声明 `network` 并限定 `hosts` 白名单后出网，未声明时网络请求被运行时拦截 |
| 插件坏了会不会让全系统下不了单 | 默认不会，`fail_mode` 为 `open` 时插件异常按放行处理；选了 `closed` 则会拒绝 |
| 绑定被自动停用后怎么恢复 | 管理员在插件管理页手动恢复，恢复后健康计数归零 |
| 插件代码更新后已运行的实例怎么办 | 已生效的拦截链保持原代码运行不中断，下次绑定解析时用新代码 |
| 要不要写单元测试 | 要，纯计算部分可以脱离框架测试，涉及 `ctx` 的部分用模拟盘实例验证 |
| 插件里能写业务词吗 | 能，业务名词只存在于设置声明里；框架层不使用任何业务词 |
