# 故障处理

> 本文档定义 BAMY 出问题时怎么定位、怎么止损、怎么恢复：按现象查原因、按级别定动作、按流程做复盘。
> 面向处理故障的人。规则与分级定义见《异常与容错》，常态巡检见《运维手册》。
> 本文档是完整设计，不是第一版，是最终态。

---

## 一、适用场景

- 系统报错、变慢、不可用
- 实例不启动、自动停止、不下单、不平仓
- 数据与交易所不一致
- 出现安全事件嫌疑

---

## 二、处置总流程

```
1. 发现（监控 / 告警 / 用户反馈）
2. 定位（日志 / 指标 / 审计 / 对账差异）
3. 止损（降级 / 熔断 / 暂停实例）
4. 修复（重启 / 回滚 / 修正数据）
5. 验证（功能恢复 / 差异收敛）
6. 复盘（根因 / 改进项）
7. 记录（审计 / 文档更新）
```

顺序不可颠倒。先止损再定位根因，是防止损失扩大的前提，尤其在实盘场景下。

---

## 三、定位手段

### 3.1 四类信息源

| 信息源 | 用来回答 |
|---|---|
| 日志 | 刚才发生了什么，哪一步失败 |
| 指标 | 是全局问题还是单实例问题，从何时开始 |
| 审计 | 谁在什么时候做了什么，是否人为触发 |
| 对账差异 | 本地与交易所差在哪，差多少 |

### 3.2 串联方法

每个请求与每个动作都带 `request_id`、`user_id`、`instance_id`。定位时先用其中一个标识把日志串成一条时间线，再对照指标的时间点，最后用审计确认是否有人工操作叠加。

---

## 四、按级别定动作

### 4.1 降级级别

| 级别 | 含义 | 触发条件 |
|---|---|---|
| L1 轻降级 | 非核心功能限流 | CPU>80% 或内存>85% 或磁盘>90% 持续 |
| L2 中降级 | 非核心功能关闭 | CPU>90% 或内存>95% 或连接池>90% |
| L3 重降级 | 只保留核心功能 | 行情全源失败、币安全面不可用 |
| L4 熔断 | 停止开仓，只允许平仓 | 对账差异超阈值 |

### 4.2 各级行为

| 级别 | 关闭什么 | 保留什么 |
|---|---|---|
| L1 | 降低日志采样与快照频率，非核心查询限流 | 全部核心功能 |
| L2 | 历史数据查询、对比功能、非关键告警 | 订单、持仓、平仓 |
| L3 | 模拟盘、审计的非关键部分 | 订单、持仓、平仓 |
| L4 | 全部开仓 | 平仓、查询 |

触发条件消失后自动分级回落，每次恢复都写审计。管理员也可手动升降级。

## 五、按现象查原因

### 5.1 应用无法启动

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动即退出并打印缺少项 | 必需配置缺失 | 补齐 `SECRET_KEY`、`ENCRYPT_KEY`、`DATABASE_URL` |
| 提示密钥长度不足或相同 | 密钥不合规 | 各生成 32 位以上且互不相同的随机值 |
| 端口被占用 | 端口冲突 | 换端口或释放占用进程 |
| 连不上数据库 | 数据库不可达或凭据错误 | 检查网络、库是否启动、连接串是否正确 |
| 迁移版本不一致 | 库结构与代码期望不符 | 执行迁移或回滚到匹配版本 |
| 依赖缺失 | 环境不完整 | 按依赖清单补齐 |

### 5.2 服务能起但接口全报错

| 现象 | 原因 | 处理 |
|---|---|---|
| 全部 401 | 登录过期或密钥被更换 | 重新登录；若刚换过 `SECRET_KEY`，旧 token 全部失效属预期 |
| 全部 403 | 角色或会话被调整 | 检查角色与会话状态 |
| 全部 503 | 系统处于启动中、关闭中或降级 | 看健康检查与降级级别 |
| 全部 500 | 未捕获异常或数据库异常 | 看应用日志堆栈 |

### 5.3 实例无法启动

| 现象 | 原因 | 处理 |
|---|---|---|
| 提示账号失效 | 密钥失效或权限不足 | 更新密钥后重试 |
| 提示策略缺失 | 策略未加载或被移除 | 重新扫描扩展，必要时换策略 |
| 提示参数非法 | 参数超出策略声明范围 | 按提示字段修正 |
| 提示对账未通过 | 存在未收敛差异 | 手动触发对账，差异收敛后再启动 |
| 停在启动中不动 | 账号探活或初始化卡住 | 查该实例日志的最后一条 |
| 提示被插件拒绝 | 拦截型插件在 `instance.before_start` 返回拒绝 | 见 5.11 |

### 5.4 实例运行中自动停止

| 原因 | 判断方式 | 处理 |
|---|---|---|
| 连续异常超过阈值 | 实例详情的连续错误计数与最后几条错误日志 | 修策略或参数，重启实例 |
| 行情延迟超阈值 | 引擎指标里的行情延迟 | 检查行情源，等待恢复 |
| 触发熔断 | 熔断列表与审计 | 处理触发原因后手动解除 |
| 账号失效 | 账号状态 | 更新密钥 |

### 5.5 下单失败

| 现象 | 原因 | 处理 |
|---|---|---|
| 余额不足 | 可用资金小于所需 | 充值或降低下单量 |
| 数量或价格精度不合法 | 不满足交易对精度 | 按交易对精度调整 |
| 名义价值低于最小值 | 单笔太小 | 提高下单量 |
| 命中限频 | 下单过密 | 等待退避完成，或降低频率 |
| 命中风控 | 限额、黑白名单、冷却 | 见对应风控规则 |
| 交易所拒绝 | 交易所业务规则 | 看返回错误码，按《错误码》处理 |

### 5.6 订单状态一直未知

1. 确认实例与账号在线。
2. 查看对账队列长度与未知订单数是否在下降。
3. 手动触发一次对账。
4. 仍未收敛时，查交易所侧订单流水，确认是否已成交。
5. 确认交易所无此单，则收敛为失败并记录差异。

未知状态不可放着不管：它会同时污染本地持仓计算与后续风控判断。

### 5.7 对账差异

| 原因 | 表现 | 处理 |
|---|---|---|
| 网络丢包导致回报丢失 | 差异零散出现 | 重新对账即收敛 |
| 交易所回报延迟 | 差异短时出现后自行消失 | 等待，不手动干预 |
| 本地状态计算错误 | 同类差异反复出现 | 按以交易所为准的规则修正，并排查代码 |
| 人工在交易所侧操作 | 差异与本地无关 | 确认操作来源，记录并保留差异痕迹 |

差异处理原则：以交易所为准修正本地，修正过程留痕，超阈值触发熔断。

### 5.8 数据库故障

| 现象 | 原因 | 处理 |
|---|---|---|
| 连接失败 | 网络、库挂掉、连接数打满 | 检查网络与库状态，必要时调整连接池 |
| 磁盘写满 | 日志或备份堆积 | 清理并调整保留策略 |
| 慢查询增多 | 索引缺失或数据量增长 | 分析慢查询，补索引 |
| 数据损坏 | 硬件或异常中断 | 从最近可用备份恢复 |

### 5.9 性能问题

| 现象 | 常见原因 | 处理 |
|---|---|---|
| CPU 高 | 对账过密、行情分发忙、慢查询 | 先看是哪类任务吃 CPU，再分别处理 |
| 内存高 | 行情缓存与上下文过多 | 检查是否有实例泄漏，收缩缓存 |
| 磁盘 IO 高 | 写入过频或日志风暴 | 降采样、加密轮转 |
| 网络慢 | 交易所侧或本机出口 | 看指标区分是本机还是外部 |

### 5.10 安全问题

| 现象 | 处理 |
|---|---|
| 越权访问记录 | 立即禁用相关账号，核查数据是否被读取 |
| 登录爆破 | 封禁来源地址，提高锁定阈值，评估强制二次验证 |
| 密钥泄露嫌疑 | 立即轮换 JWT 与加密密钥，轮换后撤销全部会话 |
| 账号密钥泄露 | 到交易所作废该密钥，重新添加，检查历史订单有无异常 |

安全事件优先止损：先切断访问，再排查范围。

### 5.11 实例启动被拒绝

**现象：** 实例停在 `error`，`last_error` 写明被某个插件拒绝，实例没有进入运行态。

**原因：** 拦截型插件在 `instance.before_start` 检查点返回 `DENY(reason)`。常见于账号等级限制、交易对黑名单、运行时段限制这类由插件配置的规则。

**定位手段：**

1. 看实例详情的 `last_error`，其中含拒绝的 `plugin_id` 与 `reason`
2. 到插件绑定列表按 `plugin_id` 筛选，确认它在哪个作用域生效
3. 审计里按实例 ID 查该次启动的拦截记录，记录含插件 ID、绑定 ID、生效作用域、结论与耗时
4. 按生效链 `account > user > global` 判断是哪一级绑定的规则命中

**恢复动作：** 按业务判断三选一：

- 规则正确 → 修改该绑定的 settings，让实例满足条件
- 规则过严 → 停用该绑定，或调低其生效作用域
- 规则有误 → 修好插件包后重新扫描扩展

`instance.before_start` 只支持放行与拒绝，不支持改写，不能靠改参数绕过。改完后再次启动实例。

### 5.12 下单被拒绝（PLUGIN_DENIED）

**现象：** 策略调用下单后订单未发往交易所，订单记为 `rejected`，来源标记为插件拦截，错误码 `PLUGIN_DENIED`。

**原因：** 拦截型插件在 `order.before_submit` 检查点返回 `DENY(reason)`。风控先于插件，因此走到这一步说明风控已放行，拒绝来自插件。

**定位手段：**

1. 看订单详情的错误码与 `reason`，以及 `plugin_id`
2. 查审计里的拦截链记录，看是链条上第几个插件、是否经过 `MODIFY`
3. 对照该绑定的 settings，确认是哪条规则命中
4. 区分拒绝与改写：`MODIFY` 不产生拒绝，只会改变订单的数量或价格

**恢复动作：**

- 规则正确 → 不动，属预期行为，按插件给出的 `reason` 去改用户侧配置
- 规则过严 → 调整该绑定的 settings，或调整 `priority` 改变链条顺序
- 规则有误 → 停用该绑定，下单立即恢复

不要为了绕过规则去改策略参数，插件拒绝与策略参数无关。

### 5.13 插件拦截超时（PLUGIN_TIMEOUT）

**现象：** 下单变慢或被拒绝，错误码 `PLUGIN_TIMEOUT`，插件健康度里超时次数增长。

**原因：** 拦截型插件在超时上限内没有返回，且该钩子的 `fail_mode` 为 `closed`，于是按拒绝处理。常见于插件在拦截钩子里做出了网调用、查询或阻塞操作。

**定位手段：**

1. 看插件健康度的平均耗时与超时次数，定位是哪个插件
2. 看审计里的拦截耗时，确认超时发生在哪个检查点
3. 检查该插件的 `timeout_ms` 与 `fail_mode` 声明
4. 确认该插件是否在 `order.before_submit` 上做了本应放到订阅型钩子里的重活

**恢复动作：**

- 止损 → 把该绑定的 `fail_mode` 调为 `open`，或停用该绑定，下单立即恢复
- 治本 → 让插件把耗时操作移出拦截路径，改由订阅型钩子异步处理
- 过渡 → 在声明的上限内调大 `timeout_ms`

调大超时只是治标：它会同时拖慢所有经过该检查点的下单。

### 5.14 插件绑定被自动停用

**现象：** 某插件绑定状态变为已自动停用，系统发过 `system.alert`，插件不再参与事件分发与拦截链。

**原因：** 该插件的连续异常次数超过阈值（默认 10 次），框架把绑定自动停用。异常包含抛错与超时两类。

**定位手段：**

1. 到插件管理页看该插件的健康度：调用次数、异常次数、平均耗时、最近错误
2. 看最近错误的原文与时间，判断是配置错、出网失败还是代码缺陷
3. 查审计里的自动停用记录
4. 确认影响面：该绑定所在作用域下的账号与实例在下单路径上已不再被拦截

**恢复动作：**

- 先修根因，再在插件管理页手动恢复绑定，恢复后健康计数归零
- 反复恢复而未修根因，会再次被自动停用
- 全局绑定恢复前，先评估其出网 hosts 与拦截规则的影响面

绑定被自动停用不影响实例的运行状态，只影响该作用域下的拦截链。

### 5.15 策略加载失败

**现象：** 策略列表中某策略状态为加载失败，实例引用该策略时启动被拒。

**原因：** `strategy.yaml` 缺失或格式错、`strategy.py` 缺失或语法错、未导出 `STRATEGY`、`STRATEGY` 未继承基类、`kind` 不为 `strategy`。

**定位手段：**

1. 在策略列表看失败原因，框架会写明缺哪个文件或哪一步校验未过
2. 确认目录名与 `id` 一致，必须文件齐全
3. 确认 `extensions/strategies/` 下有该目录，且未以 `__` 开头
4. 注意能力声明缺对应方法、未知参数类型这两类只记警告，不会让整个策略加载失败

**恢复动作：**

- 修好策略文件后触发"重新扫描扩展"
- 加载失败时框架保留旧版本，正在运行的实例不受影响
- 引用该策略的新实例在修好前无法启动
- 策略已被移除时，其所有实例必须先停止

## 六、告警级别与响应

| 级别 | 含义 | 通知方式 | 响应要求 |
|---|---|---|---|
| P0 | 系统不可用 | 立即，电话或短信 | 立刻介入 |
| P1 | 核心功能受影响 | 立即，邮件加 Webhook | 尽快介入 |
| P2 | 部分功能受影响 | 邮件加 Webhook | 当日处理 |
| P3 | 轻微问题 | 后台通知 | 按排期处理 |

典型对应：

| 条件 | 级别 |
|---|---|
| 引擎崩溃、数据库不可用、币安全面不可用 | P0 |
| 账号失效、熔断触发、实例自动停止、保护单缺失、对账差异超阈值 | P1 |
| 插件绑定被自动停用、全局绑定的插件加载失败 | P1 |
| 连续错误达警告阈值、限频接近上限、行情延迟、资源使用率高 | P2 |
| 插件平均耗时升高、插件拦截超时次数增长、单个用户的插件触发异常 | P2 |
| 登录失败 | P3 |

同类告警短时间内只发一次，关联告警合并，已处理的告警不再重复推送。

## 七、恢复动作对照

| 场景 | 动作 |
|---|---|
| 单实例异常 | 停止并重启该实例 |
| 多实例异常且同源 | 先止损（降级或熔断），再定位公共依赖 |
| 账号失效 | 更新密钥，然后恢复该账号下的实例 |
| 行情中断 | 切备用源；无法切换时停止开仓 |
| 连接断开 | 自动重连并补拉状态，人工确认是否恢复 |
| 进程崩溃 | 重启后先对账再恢复实例 |
| 数据不一致 | 以交易所为准修正本地，记录差异 |
| 配置改错 | 改回正确值并重启相关组件 |
| 插件拒绝下单 | 先确认规则是否预期，再决定调整设置、停用绑定还是修插件 |
| 插件绑定被自动停用 | 修根因后再在插件管理页手动恢复，恢复后健康计数归零 |

崩溃恢复的顺序固定：扫描需要恢复的实例，先对账，再逐个恢复，超时或失败的不勉强恢复，记入失败列表并告警。

## 八、重试原则

| 类别 | 是否重试 | 说明 |
|---|---|---|
| 网络超时 | 是 | 退避重试，超上限转对账 |
| 交易所限频 | 是 | 按退避时间等待 |
| 交易所业务拒绝 | 否 | 重试也不会成功，直接失败 |
| 数据库连接失败 | 是 | 有限次重试后进入降级 |
| 参数校验失败 | 否 | 属于请求错误 |
| 状态冲突 | 否 | 需要先改变状态 |
| 插件拒绝 | 否 | 规则未变则结果不变，改了规则再重试 |

停止条件：达到最大次数、达到总时长上限、或错误类型判定为不可重试。重试必须有上限，无上限的重试等于放弃失败。

---

## 九、复盘

1. 记录现象、影响范围、起止时间。
2. 记录定位过程与关键证据。
3. 写明根因，区分直接原因与根本原因。
4. 列出改进项，每项指定责任与期限。
5. 更新本文档或相关设计文档，让同类问题有据可查。

复盘只写事实与改进，不写责任认定。

## 十、常见问题

| 问题 | 回答 |
|---|---|
| 能不能直接改数据库修数据 | 能但要极其谨慎：先备份，改完必须触发对账，并写审计 |
| 实例恢复失败一直重试吗 | 不，超过上限即记入失败列表并告警，避免拖垮启动 |
| 熔断能自动解除吗 | 差异类熔断在差异收敛后可解除；人工触发或严重事件的熔断需人工确认 |
| 降级要不要通知用户 | 影响用户可感知功能的降级应通过公告或页面提示告知 |
| 交易所挂了怎么办 | 停止开仓，等待恢复，期间依靠对账收敛状态，不做补偿性下单 |
| 能不能先在预发复现再处理生产 | 可以，但生产正在扩大损失时先止损，再谈复现 |
| 插件拒绝下单能绕过吗 | 不能，也不应绕过；插件拿不到下单接口，框架也不提供关闭拦截的开关，只能改规则或停用绑定 |
| 插件超时会不会拖垮全系统 | 不会，插件与框架、策略之间失败隔离；影响只限该插件所在作用域的下单路径 |
