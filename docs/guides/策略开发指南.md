# 策略开发指南

> 本文档教如何从零写一个 BAMY 策略并让它跑起来：目录怎么摆、元信息怎么写、参数怎么声明、策略类怎么实现、怎么调试、怎么发布。
> 规则本身见《策略规范》，本文档只讲怎么用这些规则。
> 本文档是完整设计，不是第一版，是最终态。

---

## 一、适用场景

需要新增一个策略时读本文档。包括：

- 新写一个策略
- 给已有策略加参数、加能力
- 调试策略为什么加载不起来
- 发布策略给其他人使用

不需要读本文档的场景：

- 只想使用已有策略，见《快速开始》。
- 想扩展框架自身的行为，而不是交易决策，见《插件开发指南》。

## 二、前置条件

### 2.1 环境

| 项 | 要求 |
|---|---|
| 运行环境 | Python 3.11 及以上 |
| 框架 | BAMY 已在本机可运行 |
| 目录 | 已存在 `extensions/strategies/` 目录 |
| 依赖 | 策略自带的第三方库写进 `requirements.txt` |

### 2.2 心智准备

三条必须先接受的规则：

1. 策略不能直接调交易所，一切下单、查询、持仓动作都通过框架提供的上下文对象 `ctx`。
2. 策略不能直接碰数据库、网络、文件系统与环境变量，框架沙箱会拦截。策略一律禁止出网。
3. 策略调 `ctx.buy` 不等于一定下到交易所，框架的检查点上可能有插件否决或改写这笔单子，见第七节。

违反前两条，策略无法加载或运行即报错。这不是限制，是让策略与实盘、模拟盘、多账号、对账机制自动兼容的前提。

## 三、五步做出第一个策略

### 3.1 第一步：建目录

```text
extensions/strategies/
  my_strategy/
    strategy.yaml
    strategy.py
    __init__.py
```

目录名就是策略 ID，规则：

- 只允许小写字母、数字、下划线
- 长度 3-32 字符
- 全局唯一（与插件 ID 不在同一命名空间，允许同名，但不建议）
- 不能以 `__` 开头

### 3.2 第二步：写 strategy.yaml

种类与元信息部分：

```yaml
kind: strategy
id: my_strategy
name: 示例策略
version: 1.0.0
author: 作者名
description: 一句话说明适用行情
tags: [spot]
min_bamy_version: 1.0.0
```

参数部分：

```yaml
params:
  - key: order_amount
    label: 每次下单量
    type: float
    default: 10.0
    min: 0.0001
    required: true
    help: 以基础币计价
    group: 基础
```

能力部分：

```yaml
capabilities:
  close_position: true
  cancel_order: true
```

运行配置：

```yaml
runtime:
  tick_interval: 1
  symbols: [BTC/USDT]
```

`kind` 必须为 `strategy`，框架靠它区分策略包与插件包。只声明真正会实现的能力，声明了 `close_position: true` 却没写对应方法，该能力不会被暴露。

### 3.3 第三步：写 strategy.py

```python
from bamy.strategy import BaseStrategy, StrategyContext


class MyStrategy(BaseStrategy):
    async def on_start(self):
        self.counter = 0

    async def on_tick(self, tick):
        self.counter += 1
        self.ctx.log_info(f"tick {self.counter} price={tick['last']}")
        if self.counter % 10 == 0:
            await self.ctx.buy(amount=self.ctx.params["order_amount"])

    async def on_stop(self):
        self.ctx.log_info("stopped")

    async def close_position(self, position_id, amount=None):
        await self.ctx.close_position(position_id, amount)

    async def cancel_order(self, order_id):
        await self.ctx.cancel(order_id)


STRATEGY = MyStrategy
```

要点：

- 类名随意，但必须继承 `BaseStrategy`
- 必须导出模块级变量 `STRATEGY`
- `on_start`、`on_tick`、`on_stop` 必须有
- 所有生命周期方法都是 `async`
- 声明了能力就必须实现同名方法

### 3.4 第四步：写 __init__.py

```python
from .strategy import STRATEGY

__all__ = ["STRATEGY"]
```

### 3.5 第五步：加载并试跑

1. 在管理员界面触发一次"重新扫描扩展"。
2. 确认策略出现在策略列表中，状态为已加载。
3. 用调试命令拿模拟行情跑一遍，观察日志：

```bash
bamy strategy dryrun my_strategy --symbol BTC/USDT
```

4. 确认日志里 `on_tick` 正常触发，没有异常计数增长。
5. 创建一个模拟盘实例挂上该策略，观察净值曲线是否符合预期。

## 四、参数怎么写

### 4.1 支持的类型

| type | 前端渲染 | 后端校验 |
|---|---|---|
| `int` | 数字框（整数） | 整数、`min`/`max` |
| `float` | 数字框（小数） | 数字、`min`/`max` |
| `string` | 文本框 | 长度、`pattern` |
| `text` | 多行文本框 | 长度 |
| `bool` | 开关 | 布尔 |
| `select` | 下拉框 | 值在 `options` 内 |
| `multiselect` | 多选框 | 值都在 `options` 内 |
| `secret` | 密码框 | 长度、存储加密 |
| `symbol` | 交易对选择器 | 合法的交易对 |
| `date` | 日期选择器 | 合法日期 |
| `time` | 时间选择器 | 合法时间 |
| `datetime` | 日期时间选择器 | 合法日期时间 |
| `duration` | 时长选择器 | 合法时长（秒/分/时） |
| `percent` | 百分比输入 | 0-100 |

写了框架不认识的 `type` 时，加载记警告、该参数被跳过，整个策略不会因此加载失败。

### 4.2 字段含义

| 字段 | 说明 |
|---|---|
| `key` | 参数键，策略里用 `ctx.params["key"]` 读 |
| `label` | 界面显示名 |
| `type` | 类型 |
| `default` | 默认值 |
| `min` / `max` | 数值范围 |
| `step` | 数值步进 |
| `required` | 是否必填 |
| `help` | 字段说明 |
| `placeholder` | 占位符 |
| `suffix` | 单位后缀，如 `%` |
| `group` | 分组名，界面按组展示 |
| `pattern` | 正则（`string`） |
| `max_length` | 最大长度（`string`/`text`） |
| `options` | 枚举项，每项含 `value` 与 `label` |
| `depends_on` | 条件显示，含 `key` 与 `value` |
| `secret` | 是否为敏感字段，界面用密码框 |

### 4.3 写参数的规矩

- 每个参数都要有 `label` 与 `help`，界面才不会出现只有键名的字段
- 有范围的数值一定写 `min` / `max`，这是框架前置校验的依据
- 互斥或联动的参数用 `depends_on` 声明，不要靠策略内部判断；依赖不满足的参数不参与必填校验，也不传给策略
- 用 `group` 把参数分到基础、高级、风险这类组里，参数多时界面才不至于一屏塞满
- 默认值必须是一个能跑起来的值，不要留空等用户填

## 五、能力与实现的对应

| 能力声明 | 必须实现的方法 | 触发场景 |
|---|---|---|
| `close_position` | `close_position(position_id, amount=None)` | 用户点平单仓 |
| `close_positions` | `close_positions(position_ids)` | 用户点平多仓 |
| `close_all` | `close_all_positions()` | 用户点一键全平 |
| `close_partial` | `close_position(position_id, amount)` | 用户填部分数量，靠 `amount` 参数生效 |
| `cancel_order` | `cancel_order(order_id)` | 用户撤单 |
| `cancel_all` | `cancel_all_orders()` | 用户撤全部 |
| `set_leverage` | `set_leverage(n)` | 框架或用户设置 |
| `set_margin_mode` | `set_margin_mode(mode)` | 框架或用户设置 |
| `set_position_mode` | `set_position_mode(mode)` | 框架或用户设置 |
| `list_positions` | `list_positions()` | 查看持仓 |
| `pause` | `pause()` | 用户点暂停 |
| `resume` | `resume()` | 用户点恢复 |
| `reset` | `reset()` | 用户点重置 |

不声明就不必实现，框架会隐藏对应按钮。

`list_positions()` 返回值必须包含稳定 ID、交易对、方向、数量、开仓均价、标记价、未实现盈亏。ID 在持仓存续期间不能变，否则用户的平仓操作会指错对象。策略也可以完全不用"仓"的概念，此时不声明 `list_positions` 即可。

## 六、生命周期与约定

### 6.1 调用顺序

```text
加载策略 → 实例化策略 → 注入 ctx → on_start()
   → 订阅行情 → on_tick(tick) 反复触发
   → （暂停时 on_pause()）→（恢复时 on_resume()）
   → 用户点停止 → on_stop() → 取消订阅
```

每次实例启动都是一个独立的策略对象，不同实例之间不共享策略对象。

### 6.2 必须知道的约定

- 同一实例的方法调用是串行的，不会并发调用 `on_tick`
- 策略抛出的异常由框架捕获、记日志、计数，连续超过阈值自动停止实例
- 异常不向上传播，一个实例出错不影响其他实例
- 策略内部耗时的操作必须 `await`，否则会阻塞该实例的调度
- `on_start` 抛异常 → 实例启动失败，状态置为出错
- `on_stop` 抛异常 → 记日志，仍视为停止成功

### 6.3 状态怎么保存

用 `ctx.state` 存实例级键值对，进程重启后仍在，用来"接着跑"：

```python
await self.ctx.state.set("last_grid_level", 3)
level = await self.ctx.state.get("last_grid_level")
```

不要用类属性保存跨重启的状态，类属性在重启后丢失，并且会被同一策略的其他实例共享。

## 七、下单意图可能被插件拦截

策略通过 `ctx` 表达交易意图，框架负责落地。这条路径上不止有策略，还有框架的检查点，而插件可以挂在检查点上。

### 7.1 调 ctx.buy 不等于成交

- `await ctx.buy(...)` 返回的是框架受理这笔意图的结果，不是交易所的成交回报。
- 框架在把意图送出前会经过检查点，插件可以在检查点上否决或改写这笔单子。
- 被改写时，实际下到交易所的数量、价格、委托类型可能与策略传入的不同。
- 被否决时，框架返回拒绝原因并记审计，对应错误码 `PLUGIN_DENIED`。

### 7.2 策略应该怎么做

- 不假定下单必然成功，检查 `ctx.buy` 的返回值。
- 以订单状态为准推进逻辑，通过 `on_order(order)` 观察订单最终是成交、被拒还是失败。
- 订单数量以框架回报为准，不要用自己传入的数值推算持仓与盈亏。
- 平仓同理，`ctx.close_position` 也可能在检查点上被拒。

### 7.3 策略不应该做什么

| 不做的事 | 原因 |
|---|---|
| 探测系统里装了哪些插件 | 框架不向策略暴露任何插件信息 |
| 为绕过插件而改写自身逻辑 | 拦截是框架的既定行为，不是异常 |
| 假定某个插件一定存在或一定不存在 | 插件由管理员与用户各自绑定，随作用域变化 |
| 把插件当成策略的一部分来配合 | 策略与插件互不可见，二者并列 |

策略作者不需要知道系统里跑着哪些插件，框架也不提供任何接口让策略感知。这与《策略规范》第十五节的契约一致：插件拦截不是契约破坏，而是契约的一部分。

## 八、调试与排错

### 8.1 常用手段

| 手段 | 用途 |
|---|---|
| `ctx.log_info` / `log_warn` / `log_error` | 在实例日志里留下痕迹 |
| `bamy strategy test <策略 ID>` | 加载策略，跑一遍校验 |
| `bamy strategy dryrun <策略 ID> --symbol <交易对>` | 用模拟数据跑 `on_tick`，不产生真实下单 |
| `bamy strategy form <策略 ID>` | 打印参数表单结构，核对渲染结果 |
| 模拟盘实例 | 验证完整下单路径与净值曲线 |
| 实例详情页的连续错误计数 | 判断是否触发自动停止 |

### 8.2 加载失败的常见原因

| 现象 | 原因 |
|---|---|
| 策略不在列表里 | 目录以 `__` 开头，或目录名不符合命名规则 |
| 提示缺少必须文件 | 少了 `strategy.yaml`、`strategy.py` 或 `__init__.py` |
| 提示未导出 STRATEGY | `__init__.py` 没有导出 `STRATEGY` |
| 提示能力不匹配 | 声明了能力但没实现对应方法 |
| 提示参数校验失败 | 参数缺少必填字段，或 `type` 不被支持 |
| 提示 kind 不对 | `strategy.yaml` 里 `kind` 缺失或不是 `strategy` |
| 解析元信息失败 | YAML 缩进错误，或 `id` 与目录名不一致 |

### 8.3 运行时的常见原因

| 现象 | 原因 |
|---|---|
| 实例启动即失败 | `on_start` 抛异常，或前置校验未通过 |
| 实例跑一会儿自动停 | 连续异常超过阈值，去看实例日志的最后几条错误 |
| 下单一直不成交 | 数量或价格精度不合法，或名义价值低于交易所最小值 |
| 下单被拒且原因是插件 | 被检查点上的插件否决，见第七节 |
| 平仓按钮点了没反应 | 未声明对应能力，或声明的能力没有实现 |
| 重启后策略行为异常 | 关键进度存了类属性而不是 `ctx.state` |

### 8.4 热更新的限制

- 策略代码被重新加载时，已运行实例不会自动换用新代码
- 需要人工停止再启动实例才会生效
- 新代码加载失败时，框架保留旧版本继续运行

## 九、安全边界

### 9.1 不能做的事

- 直接 import 交易所库（如 ccxt）
- 直接访问网络
- 直接访问数据库
- 读写其他实例的上下文
- 读环境变量
- 写策略目录以外的文件
- 使用 `subprocess`、`eval`、`exec`

### 9.2 为什么

策略代码是用户可见、可替换的。这些规则让策略只通过 `ctx` 与外界交互，从而在实盘与模拟盘之间自动通用。沙箱只防误操作，不防恶意代码，策略与框架同进程运行，只安装可信来源的策略包，见《策略规范》第十一节。

### 9.3 违规的后果

| 行为 | 结果 |
|---|---|
| 导入白名单之外的模块 | 加载失败并记录原因 |
| 运行期触碰被拦截的操作 | 抛异常，计入连续错误计数 |
| 反复违规 | 实例被自动停止，事件记入审计 |

## 十、发布

### 10.1 版本规则

- 用语义化版本：不兼容变更升主版本，新增功能升次版本，修 bug 升补丁
- 主版本变更须在说明里写清不兼容点
- 声明 `min_bamy_version`，避免在不支持该策略的框架上运行

### 10.2 发布内容

| 文件 | 必须 |
|---|---|
| `strategy.yaml` | 是 |
| `strategy.py` | 是 |
| `__init__.py` | 是 |
| `requirements.txt` | 有第三方依赖时 |
| `README.md` | 是，说明适用行情、参数含义、风险提示 |

### 10.3 兼容性检查

发布前逐项确认：

1. 所有声明的能力都有实现
2. 所有参数都有 `label`、`help`、合理的默认值
3. 在模拟盘上完整跑通启动、下单、平仓、停止
4. 连续运行一段时间，错误计数保持为零
5. 不假定下单必然成交，订单状态与数量的处理以框架回报为准
6. `README.md` 里写清了风险与适用边界

## 十一、常见问题

| 问题 | 回答 |
|---|---|
| 策略能直接调交易所下单吗 | 不能，必须走 `ctx`，否则实盘与模拟盘无法共用同一份代码 |
| 一个策略能同时支持现货和合约吗 | BAMY 只做币安现货，`market_type` 当前只接受 `spot`；U 本位合约为预留扩展位，未实现 |
| 策略能自己画界面吗 | 能，放进 `static/` 目录，但表单仍以参数声明为主 |
| 参数改了会不会影响正在运行的实例 | 修改参数会触发实例的重新校验，具体见《实例模型设计》 |
| 策略能调另一个策略吗 | 不能，实例之间完全隔离，共用逻辑应各自实现或放进策略自己的 `helpers/` |
| 策略能感知插件吗 | 不能，框架不暴露插件与拦截结果，策略按"意图已表达"继续走即可 |
| 策略能出网吗 | 不能，一律禁止；需要出网的动作只能由插件在声明白名单后完成 |
| 返回 `ALLOW` / `DENY` 是策略的事吗 | 不是，那是插件拦截型钩子的返回值，策略不参与拦截协议 |
| 要不要写单元测试 | 要，纯计算部分可以脱离框架测试，涉及 `ctx` 的部分用模拟盘验证 |
