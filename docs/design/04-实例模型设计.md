BAMY 实例模型设计

本文档是 BAMY 框架的第四份设计文档，定义：实例是什么、由什么组成、状态如何变化、生命周期如何流转、如何启动、如何停止、如何换插件、如何删除、如何崩溃恢复、如何被用户和管理员操作。
不写代码，只写规则和逻辑。本文档是完整设计，不是第一版，是最终态。

二、实例是什么

2.1 定义

实例 = 账号 + 插件 + 参数 + 交易对 + 模拟/实盘标志 + 一组运行状态。

它是 BAMY 里唯一在运行的东西。用户不跑策略、账号不跑策略、插件不跑策略，只有实例在跑。

2.2 实例不是什么

· 实例不是插件。插件是模板，实例是模板的一次运行。
· 实例不是账号。账号是接入单位，实例是使用单位。
· 实例不是订单。订单是实例跑出来的产物。

2.3 实例在系统中的位置

```
用户
 └── 账号（1:N）
 └── 插件（全局共享）
 └── 实例（1:N，每个实例绑定一个账号或为模拟盘，引用一个插件）
      └── 订单 / 持仓 / 日志 / 快照
```

一个用户可以有多个实例，每个实例独立配置、独立运行、独立记录。

2.4 实例的核心原则

实例是唯一运行单元，实例的生命周期是系统的主线。

框架围绕实例的创建、启动、运行、暂停、恢复、停止、删除、崩溃恢复，组织所有逻辑。

三、实例的组成

3.1 字段清单

字段 类型 必填 说明
id 整数 是 主键，系统生成
owner_id 整数 是 所属用户 ID
name 字符串 是 实例名，用户填，同用户内唯一
account_id 整数 否 绑定的账号 ID；模拟盘为 null
plugin_id 字符串 是 引用的插件 ID
plugin_version 字符串 是 创建时插件版本
symbol 字符串 是 交易对，如 BTC/USDT
market_type 字符串 是 spot / futures / delivery
paper 布尔 是 是否模拟盘
paper_balance 浮点 否 模拟盘初始资金（paper=true 时必填）
paper_config JSON 否 模拟盘配置（手续费、滑点等）
params JSON 是 用户填的参数（对应插件 schema）
enabled 布尔 是 是否启用（用户点击启动后置 true）
status 字符串 是 当前状态（见第四节）
stop_action 字符串 是 停止时动作：keep / close
last_started_at 时间 否 最近一次启动时间
last_stopped_at 时间 否 最近一次停止时间
last_error 字符串 否 最近一次错误信息
consecutive_errors 整数 是 连续错误计数
created_at 时间 是 创建时间
updated_at 时间 是 更新时间
deleted_at 时间 否 软删除时间

3.2 字段分组

分组 字段
身份 id、owner_id、name
绑定 account_id、plugin_id、plugin_version、symbol、market_type
模式 paper、paper_balance、paper_config
配置 params、stop_action
状态 enabled、status、last_started_at、last_stopped_at、last_error、consecutive_errors
元数据 created_at、updated_at、deleted_at

3.3 实例的唯一性

· id 全局唯一
· (owner_id, name) 唯一（同一用户下实例名不重复）
· 一个用户可以有多个实例绑定同一个账号
· 一个用户可以有多个实例引用同一个插件
· 不限制同一账号、同一交易对、同一插件的实例数量（由用户自己决定）

3.4 实例和账号的关系

· 实盘实例必须绑定一个账号
· 模拟盘实例不绑定账号
· 一个账号可以有多个实例在用
· 账号失效时，其所有实盘实例自动暂停

3.5 实例和插件的关系

· 每个实例引用一个插件
· 引用时记录创建时的插件版本
· 插件升级后，旧实例继续用旧版本（可选：允许用户手动升级到新版本）
· 插件被卸载时，其所有实例必须先停止

3.6 实例和订单、持仓、日志的关系

· 一个实例可以有多个订单
· 一个实例可以有多个持仓（由插件定义持仓结构）
· 一个实例可以有多条日志
· 订单、持仓、日志都冗余存储 instance_id，便于查询

四、实例的状态

4.1 状态列表

状态 含义
created 已创建，未启动
starting 正在启动（过渡态）
running 正在运行
pausing 正在暂停（过渡态）
paused 已暂停
resuming 正在恢复（过渡态）
stopping 正在停止（过渡态）
stopped 已停止
error 出错（启动失败或运行时致命错误）
deleted 已软删除

4.3 状态说明

状态 能否接行情 能否下单 用户可操作
created 否 否 启动、编辑、删除
starting 否 否 等待
running 是 是 暂停、停止、平仓、改参数
pausing 否 否 等待
paused 否 否 恢复、停止
resuming 否 否 等待
stopping 否 否 等待
stopped 否 否 启动、编辑、换插件、删除
error 否 否 查看错误、重试启动、删除
deleted 否 否 无

4.4 过渡态的意义

过渡态（starting/pausing/resuming/stopping） 表示操作正在进行。用户在这些状态下不能发起新操作，必须等待过渡完成。

过渡态的原因：

· 启动需要校验账号、初始化策略、订阅行情，可能耗时
· 暂停/恢复需要保存/加载状态
· 停止可能需要平仓、撤单

过渡态有超时：

· starting：30 秒
· pausing：10 秒
· resuming：10 秒
· stopping：60 秒（平仓可能慢）

超时后：

· 状态置 error
· 记录超时原因
· 通知用户

五、实例如何创建

5.1 创建的前置条件

用户创建实例时，后端校验：

检查 不通过的处理
用户已登录 401
实例数未超限 400，提示上限
实例名同用户内唯一 400，提示重名
插件存在且已加载 400，提示插件不可用
账号存在且属于本人（实盘） 404（不暴露存在性）
账号状态为在线（实盘） 400，提示账号异常
账号非只读（实盘可交易） 400，提示只读账号不能实盘
交易对合法 400
交易对与插件 runtime 声明兼容 400
market_type 与账号交易类型一致 400
模拟盘时 paper_balance > 0 400
参数按插件 schema 校验通过 400，提示具体字段
参数中必填项已填 400
参数依赖条件满足（depends_on） 400

5.2 创建流程

1. 用户提交创建请求
2. 后端执行上述校验
3. 全部通过：
   · 生成实例 ID
   · 记录 plugin_version（当前插件版本）
   · 参数与默认值合并（未填的用 schema 默认值）
   · 状态置 created
   · 存库
   · 记录审计
4. 返回实例详情

5.3 创建的连带动作

· 不自动启动（用户手动启动）
· 不创建模拟账户（启动时才创建）
· 不订阅行情（启动时才订阅）

5.4 创建的限制

限制 默认值 可配
每用户实例数上限 50 是
系统总实例数上限 1000 是
每账号绑定的实例数上限 10 是

超过限制返回明确错误，不静默截断。

六、实例如何启动

6.1 启动的前置检查

用户点“启动”时，后端严格按顺序检查：

1. 实例状态是 created / stopped / error 吗？
2. 插件还加载着吗？
3. 插件版本和实例记录的一致吗？（不一致则用实例记录的版本启动）
4. 参数按插件 schema 再校验一遍
5. 实盘：账号状态是在线吗？
6. 实盘：账号非只读吗？
7. 实盘：账号是否需要重新对账？（最近对账时间超过阈值则触发对账）
8. 实盘：账号是否被熔断？
9. 模拟盘：初始化模拟账户（首次启动）
10. 交易对是否合法？
11. 是否达到该账号的实例并发上限？

6.2 启动流程

```
用户点启动
  ↓
状态 created/stopped/error → starting
  ↓
【前置检查】（任一项失败 → error）
  ↓
【对账】（实盘；模拟盘跳过）
  ↓
【创建策略上下文】
  ↓
【实例化策略对象】
  ↓
【调 on_start()】（异常 → error）
  ↓
【订阅行情】
  ↓
【启动完成】
  ↓
状态 starting → running
  ↓
记录 last_started_at、清空 last_error、consecutive_errors 归零
  ↓
通知用户（WebSocket）
```

6.3 启动失败的分类

失败类型 状态 可重试
前置检查失败 error 是，修正后可重试
对账失败 error 是，稍后重试
策略 on_start 异常 error 是，修复策略后可重试
行情订阅失败 error 是，稍后重试
系统资源不足 error 是，稍后重试

6.4 启动的并发控制

· 同一实例同时只能有一个启动任务
· 用户重复点击启动 → 幂等返回“启动中”
· 系统批量启动多个实例 → 按队列串行执行

6.5 启动的超时

· 启动任务超时时间：30 秒
· 超时 → 状态置 error
· 启动过程中，用户不能对该实例做其他操作

七、实例如何运行

7.1 运行时的行为

运行态（running）下：

· 行情中心推送 tick → 框架调 on_tick(tick)
· 策略调 ctx.buy / ctx.sell → 框架接管下单流程
· 策略调 ctx.log → 框架记录日志
· 策略调 ctx.state.set → 框架持久化状态
· 订单状态变化 → 框架调 on_order(order)
· 用户点平仓 → 框架调对应的能力方法
· 用户点暂停 → 进入暂停流程
· 用户点停止 → 进入停止流程

7.2 运行时的异常处理

情况 处理
on_tick 抛异常 记日志、计数 +1
连续异常达阈值（默认 5） 自动停止实例，状态 error
下单失败 走订单模块异常处理
行情中断 暂停 on_tick 调用，告警，恢复后继续
账号失效 自动暂停实例，状态 error
风控熔断 停止开仓，允许平仓

7.3 运行时的状态保存

· 策略可通过 ctx.state 保存内部状态
· 状态写入数据库，进程重启后仍保留
· 每次 ctx.state.set 立即持久化（或批量延迟，可配）
· 状态有大小限制（默认 64KB/实例）

7.4 运行时的并发

· 同一实例的 on_tick 不会并发调用
· 同一实例的 on_tick 和 on_order 不会并发调用
· 框架用实例级锁保证串行
· 不同实例之间完全并行

7.5 运行时的资源限制

资源 限制
单次 on_tick 最长执行时间 5 秒，超时中止
单实例内存占用 100MB（软限制）
单实例状态存储大小 64KB
单实例每分钟下单次数 可配（默认 60）

八、实例如何暂停和恢复

8.1 暂停

暂停时：

· 停止接收行情（取消订阅）
· 不再调用 on_tick
· 保留持仓（不自动平仓）
· 保留挂单（不自动撤单）
· 保留保护单（如果存在）
· 调用 on_pause()（如果插件实现）
· 状态 running → pausing → paused

8.2 恢复

恢复时：

· 重新订阅行情
· 恢复调用 on_tick
· 调用 on_resume()（如果插件实现）
· 状态 paused → resuming → running

8.3 暂停与停止的区别

项目 暂停 停止
持仓 保留 按 stop_action 决定
挂单 保留 按 stop_action 决定
行情订阅 取消 取消
策略对象 保留在内存 销毁
状态数据 保留 保留
是否自动恢复 不 不
启动速度 快 慢

暂停 = 停一停；停止 = 结束这一轮。

8.4 暂停的应用场景

· 用户临时不想让实例跑（如出差、行情不明）
· 系统检测到异常，暂停等待人工介入
· 账号探活失败，暂停相关实例

8.5 自动暂停

以下情况自动暂停：

情况 自动暂停
账号探活连续失败达阈值 是
账号失效 是
账号被熔断 是
系统全局熔断 是
行情长时间中断 是

自动暂停不自动恢复，需用户手动。

九、实例如何停止

9.1 停止的前置检查

· 实例状态是 running / paused / error 吗？
· 没有正在进行的启动/暂停/恢复任务吗？

9.2 停止流程

```
用户点停止
  ↓
状态 → stopping
  ↓
【取消行情订阅】
  ↓
【调 on_stop()】（异常不阻塞停止）
  ↓
【按 stop_action 处理】
  ├─ keep：保留持仓和挂单
  └─ close：调用插件的 close_all_positions（或框架兜底平仓）
  ↓
【保存策略状态】（ctx.state 已持久化）
  ↓
【销毁策略对象】
  ↓
状态 → stopped
  ↓
记录 last_stopped_at
  ↓
通知用户
```

9.3 stop_action 的两种模式

模式 含义
keep 保留持仓和挂单，下次启动继续
close 停止前平掉所有仓、撤掉所有单

用户在创建或编辑实例时选择。

9.4 停止失败的分类

失败类型 处理
平仓部分失败 记录哪些成功、哪些失败，状态置 error
平仓全部失败 状态置 error，保留 stopping 前的状态
on_stop 异常 记录，仍视为停止成功

9.5 停止的超时

· 停止任务超时：60 秒
· 超时 → 状态置 error，提示用户手动检查
· 不强杀线程（避免数据不一致）

9.6 强制停止

管理员可以“强制停止”任意实例：

· 跳过平仓步骤
· 直接销毁策略对象
· 状态置 stopped
· 记录审计（谁强停的）

用户不能强制停止自己的实例（避免误操作）。

十、实例如何换插件

10.1 换插件的定义

换插件 = 把实例的 plugin_id 换掉，参数重新填，持仓和挂单要有交代。

10.2 换插件的前置条件

条件 说明
实例状态是 stopped / error running 时禁止换
实例没有未平持仓 有则先平仓
实例没有未撤挂单 有则先撤单
新插件存在且已加载 否则拒绝
新插件支持当前交易对 否则拒绝

10.3 换插件的流程

```
用户点换插件
  ↓
【前置检查】
  ↓
【检查当前持仓】
  ├─ 无持仓 → 直接换
  └─ 有持仓 → 触发保护平仓
        ↓
      【调插件的 close_all_positions 或框架兜底平仓】
        ↓
      ├─ 成功 → 继续换
      └─ 失败 → 中止换插件，状态 error
  ↓
【换 plugin_id】
  ↓
【清空旧参数】（因为参数结构不同）
  ↓
【用户填新参数】
  ↓
【校验新参数】
  ↓
【保存】
  ↓
状态回到 stopped
```

10.4 换插件时的参数处理

· 旧参数全部丢弃
· 新参数按新插件的 schema 重新填
· 不继承（因为参数 key 可能完全不同）
· 用户可以复制旧参数的“值”手动填到新参数（体验层，不是系统层）

10.5 换插件的审计

必须记录：

· 谁换的
· 什么时候
· 从什么插件换到什么插件
· 平仓结果（如果触发了平仓）

10.6 换插件的限制

· 一个实例换插件频率限制（默认每小时 5 次）
· 换插件不改变实例 ID、owner_id、账号绑定
· 换插件不改变实例名

十一、实例如何删除

11.1 删除的前置条件

条件 不通过的处理
实例状态是 stopped / error / created running/paused 时禁止删，提示先停
没有未平持仓 提示先平仓
没有未撤挂单 提示先撤单

11.2 软删除

默认是软删除。

· 状态置 deleted
· deleted_at 记录时间
· 数据保留
· 关联订单、持仓、日志保留
· 分享 token 全部撤销
· 策略状态（ctx.state）保留

软删除的实例不显示在默认列表，但可以通过“显示已删除”查看。

11.3 硬删除

只有 super_admin 可以硬删除。

硬删除流程：

1. 必须是软删除状态
2. 二次确认（输入实例名）
3. 检查无持仓、无挂单
4. 级联删除：实例、订单、持仓、日志、快照、策略状态、分享 token
5. 记录审计
6. 不可恢复

11.4 删除的连带动作

动作 说明
撤销分享 token 软删除时执行
停止行情订阅 如果还在运行（不应发生）
清理内存 如果有缓存
记录审计 记录谁删的、什么时候

11.5 删除的数据保留期

软删除后：

· 实例信息：永久
· 关联订单：按订单保留策略
· 关联日志：按日志保留策略
· 关联快照：按快照保留策略
· 策略状态：保留

硬删除后：全部立即删除，不可恢复。

十二、实例如何崩溃恢复

12.1 崩溃的场景

场景 说明
进程被杀 服务进程异常退出
服务器断电 物理中断
数据库连接断开 无法写库
系统级异常 未捕获的 bug

12.2 恢复的时机

服务重启后立即扫描：

· 所有 enabled = true 且状态为 running / starting / pausing / resuming / stopping 的实例
· 这些实例在崩溃前是“应该在运行”的

12.3 恢复的流程

```
服务启动
  ↓
【扫描需要恢复的实例】
  ↓
【对每个实例】
  ├─ 状态先置 stopped
  ├─ 对账（实盘：拉币安持仓、挂单，修正本地）
  ├─ 加载插件
  ├─ 创建策略上下文
  ├─ 实例化策略对象
  ├─ 调 on_start()（策略自己决定是否从 ctx.state 恢复）
  ├─ 订阅行情
  └─ 状态 running
  ↓
【恢复完成】
  ↓
记录审计（"崩溃恢复"）
```

12.4 恢复时的对账

恢复时对账是强制的（实盘）：

· 拉取币安的所有持仓
· 拉取币安的所有挂单
· 与本地记录比对
· 差异以币安为准修正
· 记录对账日志

对账未完成，不恢复运行。

12.5 恢复失败的分类

失败类型 处理
账号失效 实例状态置 error，通知用户
插件缺失 实例状态置 error，通知管理员
对账失败 实例状态置 error，稍后重试
策略 on_start 异常 实例状态置 error

12.6 恢复的限制

· 恢复任务并发上限（默认 5 个实例同时恢复）
· 恢复总时间限制（默认 5 分钟）
· 超过限制的实例排队等待

12.7 恢复的开关

系统配置项 AUTO_RECOVER_ON_BOOT：

· true（默认）：自动恢复
· false：不自动恢复，需用户手动启动

12.8 用户被禁用时的恢复

如果用户在崩溃前已被禁用：

· 不恢复其实例
· 状态置 disabled

12.9 账号失效时的恢复

如果账号在崩溃前已失效：

· 不恢复其实例
· 状态置 error

十三、实例和账号、插件、订单、持仓的关系

13.1 实例和账号

· 实盘实例必须绑定账号
· 模拟盘实例不绑账号
· 一个账号可以有多个实例
· 账号失效时，其实例自动暂停

13.2 实例和插件

· 每个实例引用一个插件
· 引用时记录插件版本
· 插件升级后旧实例用旧版本
· 插件卸载前必须先停相关实例

13.3 实例和订单

· 一个实例的订单必须带 instance_id
· 订单的其他字段从实例继承（account_id、symbol、owner_id）
· 一个实例的订单可以被单独查询
· 用户的所有订单 = 所有实例的订单

13.4 实例和持仓

· 持仓由插件定义（通过 list_positions）
· 框架不解释持仓的业务含义
· 持仓的 ID 由插件维护
· 用户操作持仓 → 框架调插件对应方法

13.5 实例和日志

· 一个实例的日志必须带 instance_id
· 日志分等级：debug / info / warn / error
· 用户可查自己实例的日志
· 管理员可查所有实例的日志

14.1 用户能做的

十五、实例的并发控制

15.1 实例级锁

每个实例有一把实例级锁，保证：

· 同一实例的操作串行
· 启动、暂停、恢复、停止不能并发
· on_tick、on_order 不能并发
· 用户操作和系统操作不能并发

15.2 状态过渡期的操作禁止

在过渡态（starting/pausing/resuming/stopping）下：

· 用户发起新操作 → 返回“操作进行中”
· 系统发起新操作 → 排队等待

15.3 跨实例的操作

· 不同实例的操作完全并行
· 批量操作（如批量启动）按队列串行执行
· 批量操作有并发上限（默认 5）

15.4 账号级锁

某些操作需要账号级锁：

· 同一账号下的多个实例同时下单 → 需要串行（避免余额冲突）
· 账号级锁的粒度：下单操作
· 账号级锁不阻塞其他操作

15.5 死锁预防

· 所有锁有超时（默认 30 秒）
· 加锁顺序固定（先账号后实例）
· 死锁检测：超时后释放并报错
