BAMY 订单与持仓设计

本文档是 BAMY 框架的第六份设计文档，定义：订单是什么、从哪来、怎么走、怎么对账、怎么结束；持仓是什么、谁定义、怎么查询、怎么平、怎么保护；两者与账号、实例、保护、风控的关系。
不写代码，只写规则和逻辑。本文档是完整设计，不是第一版，是最终态。

二、订单是什么

2.1 定义

订单 = 一次交易意图的记录。 它由策略产生、由框架执行、由币安或模拟引擎处理。

订单是 BAMY 里所有“动作”的最小单位。一次下单、一次撤单、一次平仓，都是一条订单。

2.2 订单不是什么

· 订单不是持仓。订单是过程，持仓是结果。
· 订单不是信号。信号是策略的意图，订单是信号的执行。
· 订单不是成交。成交是订单的最终状态之一，不是订单本身。

2.3 订单的类型

类型 说明
开仓单 建立新仓位
平仓单 减少或关闭仓位
撤单 撤销未成交订单
改单 修改订单参数（部分交易所支持）
保护单 止损、止盈、追踪止损
强平单 交易所强制平仓（由交易所触发）

2.4 订单的来源

来源 说明
strategy 策略代码调用 ctx.buy / ctx.sell 产生
manual 用户点击平仓、开仓按钮产生
guard 保护中心自动产生（保护单触发）
system 系统产生（对账修正、熔断平仓）
admin 管理员操作产生
exchange 交易所产生（强平）

订单的 source 字段必须记录来源，用于审计和区分。

side 字符串 是 buy / sell
position_side 字符串 否 long / short / none
type 字符串 是 market / limit / stop_market / ...
amount 浮点 是 数量
price 浮点 否 委托价（市价单为 null）
stop_price 浮点 否 触发价（止损单用）

3.2 字段分组

分组 字段
身份 id、client_order_id、exchange_order_id
归属 instance_id、owner_id、account_id
交易 symbol、market_type、side、position_side、type
价格数量 amount、price、stop_price
成交 filled_amount、filled_price、fee、fee_currency
状态 status、source、reason
保护 is_guard、guard_type
原始 raw_request、raw_response
时间 created_at、submitted_at、filled_at、canceled_at、updated_at

3.3 client_order_id 的设计

每条订单必须有本地唯一 ID。 用于：

· 下单幂等（同一 ID 不重复下）
· 对账定位（用 ID 查币安）
· 崩溃恢复（用 ID 追踪未完成订单）

格式：{instance_id}-{timestamp}-{random}

例如：123-1690000000000-a1b2c3

3.4 订单的不可变性

以下字段创建后不可修改：

· id
· client_order_id
· instance_id
· owner_id
· account_id
· symbol
· market_type
· created_at

其余字段在生命周期内可被更新。

3.5 订单的软删除

订单不做软删除。订单是历史记录，永久保留（按保留策略）。

五、订单从哪来

5.1 从策略来

策略调用 ctx.buy / ctx.sell：

```
策略 → ctx.buy(amount, price)
         ↓
     订单中心 → 生成订单
         ↓
     前置校验 → 风控 → 余额
         ↓
     发送币安
         ↓
     写库
```

5.2 从用户来

用户点击平仓、开仓按钮：

```
用户 → 前端 → 后端接口
                ↓
          【检查策略能力】
                ↓
          调策略的对应方法
                ↓
          策略内部调 ctx.buy/sell
                ↓
          走订单中心的完整路径
```

用户操作不绕过订单中心。 所有订单必须经订单中心。

5.3 从保护中心来

保护单触发：

```
保护中心 → 检测触发条件
              ↓
         生成订单（is_guard=true）
              ↓
         走订单中心的完整路径
```

5.4 从系统来

系统对账修正、熔断平仓：

```
对账引擎/风控中心 → 生成订单（source=system）
                       ↓
                  走订单中心的完整路径
```

5.5 从交易所来

币安强平：

```
用户数据流 → 收到强平事件
              ↓
         生成订单（source=exchange）
              ↓
         直接写库（不经过前置校验）
```

交易所产生的订单不经过前置校验（因为已经发生了），只做记录。

六、一条订单的完整生命周期

6.1 阶段 1：前置校验

在本地执行，不碰币安。

检查项 说明
实例状态 running？
账号状态 在线？非只读？
交易对有效 币安支持？
amount 合法 0？符合精度？
price 合法 符合精度？
风控规则 单笔、单日、白名单、仓位
余额 够不够（实盘查币安，模拟盘查本地）
频率 最近下单次数是否超限
幂等 client_order_id 是否重复

任一失败 → 订单状态置 rejected，记录原因，不发送币安，结束。

6.2 阶段 2：插件拦截

本地执行，在发出请求之前。风控通过后才进入本阶段。

流程：

```
订单 payload（实例、交易对、方向、数量、价格、类型）
  ↓
【取 order.before_submit 检查点上的拦截链】
  ↓
【为空 → 直接放行】
  ↓
【按 priority 顺序逐个执行插件钩子】
  · ALLOW  → 继续下一个
  · MODIFY → 替换 payload，继续下一个
  · DENY   → 立即终止
  · 异常或超时 → 按该钩子的 fail_mode
  ↓
【返回最终结论】
```

三种结局：

| 结局 | 处理 |
|---|---|
| 放行 | 用原 payload 或改写后的 payload 继续 |
| 拒绝 | 订单状态置 rejected，记录 `intercepted_by` 与 `intercepted_action`，不发送币安，发事件 order.rejected |
| 改写 | payload 被替换，后续阶段使用新值；订单落库时记录 `intercepted_by` 与 `intercepted_action` |

约束：

- 风控中心固定在本阶段之前执行。风控是系统硬约束，插件是可选增强
- 拦截链串行执行，任一插件拒绝，后续插件不再执行
- 检查点为空时本阶段无开销，直接跳入下一阶段
- 拦截结论全部记审计，含插件 ID、生效作用域、结论、耗时

本阶段可能改写 amount、price、type，不改变 symbol、side、instance_id。

6.3 阶段 3：发送币安

· 状态从 pending 变 submitting
· 调连接池的 create_order
· 超时时间：10 秒
· 三种结局：
  · 明确成功
  · 明确失败
  · 超时/网络错/状态未知

6.4 阶段 4：处理返回

成功：

· 记录 exchange_order_id
· 状态变 submitted
· 记录 submitted_at
· 发事件 order.submitted

明确失败：

· 状态变 rejected
· 记录原因（币安原话）
· 不重试
· 发事件 order.rejected

状态未知：

· 状态变 unknown
· 进对账队列
· 发事件 order.unknown

6.5 阶段 5：成交回报

通过 WebSocket 接收：

· 用户数据流收到 executionReport
· 解析：订单 ID、成交状态、成交量、成交价
· 更新本地订单：
  · 部分成交 → partial
  · 完全成交 → filled
· 更新持仓（见第八节）
· 发事件 order.filled / order.partial

通过 REST 轮询（兜底）：

· 如果 WebSocket 断线
· 定时查 submitted 状态的订单
· 更新状态

6.6 阶段 6：结束

订单进入终态后：

· 不再变更
· 记录所有时间戳
· 更新持仓
· 发事件
· 写审计

6.7 完整时序

```
策略/用户/保护/系统
       ↓
   订单中心 → 生成订单（pending）
       ↓
   前置校验 → 通过
       ↓
   风控中心 → 通过
       ↓
   【插件拦截 order.before_submit】
       ├─ 拒绝 → rejected（记录 intercepted_by），结束
       └─ 放行或改写 → 继续
       ↓
   连接池 → 发送币安（submitting）
       ↓
   币安返回
       ├─ 成功 → submitted
       ├─ 失败 → rejected
       └─ 未知 → unknown
       ↓
   WebSocket 回报
       ├─ 部分成交 → partial
       └─ 完全成交 → filled
       ↓
   更新持仓
       ↓
   发事件 → 审计 + WebSocket 推送
```

七、订单的异常处理

7.1 前置校验失败

原因 处理
实例未运行 拒绝，状态 rejected
账号异常 拒绝
参数错 拒绝
风控触发 拒绝，记录风控规则
余额不足 拒绝
频率超限 拒绝，提示稍后

所有前置失败都不发送币安，直接写 rejected。

7.2 发送失败

原因 处理
币安明确拒绝 rejected，不重试
币安 5xx 重试 3 次，全失败则 unknown
网络超时 unknown，进对账队列
限频 429 退避重试
限频 418 冷却该账号
认证失败 401 立即停止该账号所有实例

7.3 被插件拦截的处理

| 情形 | 处理 |
|---|---|
| 插件返回 DENY | 订单置 rejected，记录 `intercepted_by`、`intercepted_action`、`reason`，不发送币安 |
| 插件改写 payload | 用新值继续，落库时记录 `intercepted_by` 与 `intercepted_action` |
| 插件钩子超时且 fail_mode 为 open | 放行，记日志、计数，订单照常发出 |
| 插件钩子超时且 fail_mode 为 closed | 置 rejected，错误码 `PLUGIN_TIMEOUT` |
| 插件钩子抛异常且 fail_mode 为 open | 放行，记日志、计数 |
| 插件钩子抛异常且 fail_mode 为 closed | 置 rejected，错误码 `PLUGIN_ERROR` |

被拦截的订单同样记审计，来源标注为插件拦截，与被风控拒绝区分。

7.4 状态未知的处理

unknown 不是终态。 必须通过对账收敛。

· 进对账队列
· 每 30 秒查一次币安
· 收敛到 filled / rejected / failed

7.5 重复下单的处理

· 用 client_order_id 去重
· 同一 ID 重复提交 → 返回已有的订单
· 幂等保证：不会因为重试下两次单

7.6 部分成交的处理

· 状态置 partial
· 剩余部分继续等待
· 用户可以撤单（撤销剩余）
· 撤单后状态：已成交部分保留，剩余部分置 canceled

7.7 撤单的处理

· 状态从 submitted/partial 变 canceling
· 调币安撤单
· 成功 → canceled
· 失败 → 恢复原状态，记录错误
· 超时 → unknown，进对账

7.8 异常的重试策略

类型 重试次数 间隔
网络超时 3 2 秒
币安 5xx 3 5 秒
币安 429 按 Retry-After -
币安 418 0（冷却） -
其他 4xx 0 -

八、订单的对账

8.1 对账类型

类型 频率 说明
unknown 订单对账 30 秒 收敛 unknown
submitted 订单核查 60 秒 核查超时未成交的
历史订单对账 每小时 核对终态订单

8.2 unknown 对账流程

```
捞所有 unknown 订单
  ↓
对每条订单：
  ├─ 用 client_order_id 查币安
  ├─ 币安返回：
  │   ├─ 找到且成交 → filled
  │   ├─ 找到且未成交 → submitted
  │   ├─ 找到且部分成交 → partial
  │   ├─ 找到且被拒 → rejected
  │   └─ 没找到 → failed
  ├─ 更新本地
  └─ 发事件
  ↓
对账完成
```

8.3 对账的差异处理

如果对账发现币安和本地不一致：

· 以币安为准
· 更新本地
· 记录差异
· 差异超过阈值 → 告警

8.4 对账的幂等性

· 同一订单重复对账，结果一致
· 对账不产生新的订单
· 对账只更新状态

8.5 对账的记录

· 每次对账写日志
· 每条差异写审计
· 差异超阈值写告警

九、持仓是什么

9.1 定义

持仓 = 实例当前持有的仓位。 它由策略定义，框架不解释业务含义。

框架不知道“仓”是什么，只知道策略通过 list_positions() 返回一个清单。

9.2 持仓的定义权

持仓的定义权在策略。

不同策略对“仓”的理解完全不一样：

· 网格策略：可能没有“仓”概念，只有分散的挂单
· 合约策略（预留）：一个交易对可能有多头仓、空头仓、双向持仓
· 多交易对策略：可能同时持有 BTC、ETH、SOL 的仓
· 加仓策略：同一交易对可能有“第 1 仓、第 2 仓、第 3 仓”

框架不能定义“仓”，只能拿到清单。

9.3 持仓清单的结构

策略通过 list_positions() 返回：

```
[
    {
        id: "pos_001",              # 持仓唯一 ID（策略编）
        symbol: "BTC/USDT",
        side: "long",               # long / short / none
        amount: 0.01,
        entry_price: 50000.0,
        mark_price: 51000.0,
        unrealized_pnl: 10.0,
        unrealized_pnl_pct: 2.0,
        leverage: 3,
        label: "第1仓",
        opened_at: 1690000000000,
    },
    ...
]
```

9.4 持仓 ID 的稳定性

· 开仓时生成
· 平仓前不变
· 平仓后失效
· 部分平仓时 ID 不变（amount 变小）

框架依赖 ID 来定位要平的仓。

十、持仓的查询

10.1 从哪查

框架不自己维护持仓。 每次查询时：

1. 调策略的 list_positions()
2. 策略返回清单
3. 框架加工（补充实时价格、盈亏）
4. 返回给调用者

10.2 补充字段

框架在策略返回的基础上补充：

字段 来源
mark_price 行情中心
unrealized_pnl 框架计算
unrealized_pnl_pct 框架计算

策略可以自己提供，框架会覆盖或保留。

10.3 查询频率

场景 频率
用户查看 实时
定时刷新 前端轮询（默认 5 秒）
对账 60 秒一次
风控 下单前

10.4 缓存的策略

· 持仓不缓存（因为策略可能随时变）
· 或者短时间缓存（1 秒），避免高频查询
· 每次查询都调策略

10.5 持仓的记录

持仓本身不落库（因为它的定义权在策略）。

但持仓的快照落库：

· 每隔 N 秒记录一次持仓快照
· 用于历史查询、对账、审计
· 快照表记录：时间、实例、持仓清单

10.6 持仓和订单的关系

· 订单是持仓的来源
· 每次订单成交 → 策略更新内部持仓
· 框架不知道策略怎么更新，只知道调 list_positions() 拿最新清单

十一、持仓的平仓

11.1 平仓的粒度

粒度 说明
平单个仓 平一个具体的仓
平多个仓 平选中的几个仓
平全部仓 平所有仓
部分平仓 平一个仓的一部分

11.2 平仓的能力声明

策略在 YAML 里声明：

```
capabilities:
  close_position: true
  close_positions: true
  close_all: true
  close_partial: true
```

声明了能力，框架才显示对应按钮。

11.3 平仓前的插件拦截

平仓动作发出前，经过 `position.before_close` 检查点：

| 结局 | 处理 |
|---|---|
| 放行 | 按原样继续 |
| 拒绝 | 平仓不执行，返回拒绝原因，记审计，记 `intercepted_by` |
| 改写 | 只允许改写 amount，用新数量继续 |

约束：

- 本检查点只支持放行与拒绝改写 amount，不允许改写 position_id 与 symbol
- 人工平仓与策略平仓走同一个检查点
- 框架兜底平仓同样经过本检查点

被拒绝时的表现：接口返回错误码 `PLUGIN_DENIED`，附 `reason` 与 `plugin_id`。

11.4 平单个仓

用户点某个仓旁边的“平仓”：

1. 前端调后端接口
2. 后端检查策略是否声明 close_position
3. 是 → 调策略的 close_position(id, amount)
4. 策略内部调 ctx.sell 走订单中心
5. 返回结果
6. 前端展示结果

11.5 平多个仓

用户勾选几个仓，点“平选中”：

1. 前端调后端接口
2. 检查策略是否声明 close_positions
3. 调策略的 close_positions([id1, id2])
4. 策略逐个平仓
5. 返回结果（每个仓的成功/失败）
6. 前端逐个展示

11.6 平全部仓

用户点“一键全平”：

1. 前端调后端接口
2. 检查策略是否声明 close_all
3. 调策略的 close_all_positions()
4. 策略平所有仓
5. 返回结果
6. 前端展示

11.7 部分平仓

用户在平仓弹窗里输入数量：

1. 默认填满仓数量
2. 用户可以改小
3. 提交 → 调策略的 close_position(id, amount)
4. 策略只平指定数量

只有策略声明 close_partial 时，才显示数量输入框。

11.8 平仓的确认

· 平单个仓：不弹窗（或轻量确认）
· 平多个仓：弹窗确认
· 平全部仓：弹窗二次确认（输入实例名或点击确认）
· 部分平仓：不弹窗

11.9 平仓的结果

结果 处理
全部成功 展示成功
部分成功 展示成功的和失败的，带原因
全部失败 展示失败原因

平仓失败不回滚（因为下单已经发生），只记录。

11.10 平仓走订单中心

所有平仓都必须走订单中心的完整路径。

不能绕过订单中心直接调币安，否则会丢失记录、对账、风控。

11.11 强制平仓（兜底）

如果策略没有声明平仓能力，但用户想平仓：

框架提供“强制平仓”兜底：

· 直接市价平掉该实例的交易对持仓
· 不依赖策略
· 明确标记为“强制平仓”
· 在审计里区分

强制平仓只在策略不支持平仓时可用。

11.12 换策略时的平仓

换策略前：

1. 检查是否有持仓
2. 有 → 触发平仓
3. 优先用策略的 close_all_positions
4. 策略不支持 → 用框架兜底平仓
5. 平仓成功 → 换策略
6. 平仓失败 → 中止换策略

十二、持仓和保护的关系

12.1 保护的定义

保护 = 为了限制亏损或锁定利润而挂出的订单。 包括：

· 止损单
· 止盈单
· 追踪止损单
· 强平保护单

12.2 保护的来源

来源 说明
策略自己挂 通过 ctx.place_protection
框架自动挂 如果实例配置了默认保护
用户手动挂 通过前端按钮

12.3 保护和订单的关系

保护单也是订单。 走订单中心的完整路径，只是标记 is_guard = true。

12.4 保护的检测

· 每隔 30 秒检查一次
· 对比本地记录的保护单和币安的实际挂单
· 币安有、本地无 → 记录异常
· 本地有、币安无 → 告警“失去保护”
· 数量不一致 → 记录差异

12.5 保护缺失的处理

保护缺失时：

· 告警（WebSocket + 邮件 + Webhook）
· 记录审计
· 可选：触发本地保护（框架兜底）
· 可选：暂停实例

12.6 保护被强平

币安强平保护单：

· 用户数据流收到事件
· 更新本地订单状态
· 更新持仓（策略自己处理）
· 记录审计
· 通知用户

12.7 本地保护（兜底）

保护接口不可用时（如限频）：

· 框架在本地记录“应该挂保护”的持仓
· 定时检查价格
· 达到触发条件 → 本地触发市价平仓
· 标记为“弱保护”

十三、持仓和风控的关系

13.1 风控对持仓的检查

下单前，风控检查：

检查 说明
总仓位上限 所有持仓总和不超过 N USDT
单币仓位上限 单币持仓不超过 N USDT
单笔金额上限 本笔订单不超过 N USDT
交易对白名单 只允许白名单内
交易对黑名单 禁止黑名单内
冷却期 某币或某实例刚触发风控，N 分钟内禁止开仓

13.2 持仓和回撤

框架根据持仓计算：

· 当前权益
· 高水位权益
· 最大回撤
· 单日亏损
· 单币亏损

达到阈值 → 触发熔断。

13.3 熔断对持仓的影响

· 熔断后：只允许平仓，不允许开仓
· 熔断后：相关实例暂停
· 用户/管理员手动解除熔断后才恢复

13.4 持仓和对账

· 定时对账持仓（60 秒）
· 与币安比对
· 差异以币安为准
· 差异超阈值 → 熔断

十四、订单和持仓的记录、查询、审计

14.1 订单的记录

· 每条订单写 orders 表
· 关键时间戳、状态、成交信息全部记录
· 原始请求和响应（raw_request、raw_response）记录
· 保留时间：永久（可配归档策略）

14.2 持仓的记录

· 持仓本身不落库（定义权在策略）
· 持仓的快照落 position_snapshots 表
· 频率：每 60 秒一次
· 保留时间：按策略（默认 90 天）

14.3 订单的查询

维度 说明
按实例 某实例的所有订单
按用户 某用户的所有订单
按账号 某账号的所有订单
按交易对 某交易对的所有订单
按状态 某状态的所有订单
按时间 时间范围内的订单
按来源 策略/手动/保护/系统

14.4 持仓的查询

· 实时查询：调策略
· 历史查询：查快照表
· 用户只能查自己实例的
· 管理员可查所有

14.5 审计

所有订单和持仓相关操作必须记审计：

操作 记录
创建订单 谁、什么来源、什么实例
订单成交 成交价、量、时间
订单失败 原因
订单撤单 谁撤的、结果
手动平仓 谁、哪个仓、数量
保护单挂载 谁挂的、什么类型
保护单触发 触发原因
对账差异 差异内容

14.6 订单和持仓的导出

· 用户可导出自己的订单和持仓历史
· 导出格式：CSV / JSON
· 管理员可导出指定用户或全部

十五、订单和持仓的边界

15.1 订单的边界

边界 说明
订单必须经订单中心 不允许绕过
订单必须有 client_order_id 幂等
订单必须有 source 审计
订单必须有 instance_id 归属
订单状态必须收敛 unknown 必须对账
订单不可修改关键字段 不可变
订单不可删除 历史保留

15.2 持仓的边界

边界 说明
持仓定义权在策略 框架不解释
持仓通过 list_positions 查询 不缓存或短缓存
持仓 ID 由策略维护 框架只依赖 ID
持仓快照落库 用于历史查询
平仓必须走订单中心 不允许绕过
平仓依赖能力声明 未声明不显示按钮
平仓失败不回滚 只记录

15.3 订单和持仓的关系

· 订单是过程，持仓是结果
· 订单成交 → 策略更新持仓
· 平仓 → 生成订单 → 成交 → 策略更新持仓
· 框架不直接维护持仓，只维护订单
