BAMY 异常与容错

本文档是 BAMY 框架的第十一份设计文档，定义：系统会遇到哪些异常、如何分类、如何检测、如何响应、如何恢复、如何降级、如何告警、如何审计，以及策略与插件的异常兜底。
不写代码，只写规则和逻辑。本文档是完整设计，不是第一版，是最终态。

三、异常的处理原则

3.1 五大原则

原则 1：安全优先
任何异常处理不得以牺牲安全为代价。宁可停止交易，不可泄露密钥。

原则 2：数据一致优先
任何异常处理不得造成数据不一致。宁可慢，不可错。

原则 3：可恢复优先
任何异常处理应当保留恢复的可能。不删除、不覆盖、可追溯。

原则 4：最小影响
异常处理应将影响限制在最小范围。单订单问题不扩散到实例，单实例问题不扩散到账号。

原则 5：可观测
所有异常必须可观测：日志、指标、告警、审计。

七、插件异常

7.1 设计意图

插件异常不得让全系统停摆。这是本节所有规则的总纲。

因此默认`fail_mode`为`open`：拦截型插件自身出错时放行，而不是拒绝。目的是让一个坏掉的插件不至于让全系统下不了单。

需要拦死的场景，由插件作者显式声明`fail_mode: closed`。插件的定义与失败语义见《插件规范》第七节，本节只列兜底规则。

7.2 加载失败

| 情况 | 处理 |
|---|---|
| 元信息解析失败 | 记入失败列表，跳过该插件 |
| 代码导入失败 | 记入失败列表，跳过该插件 |
| 声明与实现不一致 | 记入失败列表，跳过该插件 |

- 失败列表管理员可见，含插件ID、失败原因、时间
- 单个插件失败不影响其他扩展（其他插件与全部策略）的加载
- 已运行实例不受影响，不因插件加载失败而停止
- 管理员修复插件文件后，手动触发重新扫描扩展

完整的加载失败清单见《插件规范》第14.1节。

7.3 绑定引用失效

绑定引用的插件不存在或加载失败时：

- 该绑定置为`invalid`
- 从生效列表移除，不再参与事件分发与拦截链
- 记审计，含绑定ID、作用域、插件ID
- 绑定不删除，插件修复后由管理员手动恢复

7.4 订阅型钩子异常

| 情况 | 处理 |
|---|---|
| 处理函数抛异常 | 记日志，计数+1 |
| 处理函数超时 | 记日志，计数+1 |

- 不影响事件的发布者
- 不影响同一事件的其他订阅者
- 主流程继续，分发为异步，不阻塞

订阅型钩子不能否决，它的失败不改变任何业务结果。

7.5 拦截型钩子异常

拦截型钩子抛异常或超时时，按绑定上的`fail_mode`处理：

| fail_mode | 处理 | 错误码 |
|---|---|---|
| `open`（默认） | 放行，记日志并告警 | 无 |
| `closed` | 拒绝，记审计 | `PLUGIN_TIMEOUT`或`PLUGIN_ERROR` |

- `open`放行时必须告警，避免问题被静默吞掉
- 两种情况都计数+1，计入健康度
- 插件主动返回`DENY`不算异常，错误码为`PLUGIN_DENIED`，不受`fail_mode`影响

7.6 连续异常超阈值

插件连续异常超过阈值（默认10次）时：

1. 绑定自动置为`disabled`
2. 发布`system.alert`事件
3. 记审计，含插件ID、绑定ID、异常次数
4. 管理员后台显示“已自动停用”，可手动恢复，恢复后计数归零

7.7 出网异常

| 情况 | 处理 |
|---|---|
| 出网被拒绝（未声明或不在白名单） | 记日志，计数+1 |
| 出网超时 | 记日志，计数+1 |

- 出网失败不影响主流程
- 出网失败计入健康度，连续超阈值同样按7.6处理

7.8 插件异常的统一策略

- 捕获所有插件异常，不扩散到框架
- 一个插件失败不影响其他插件、策略与实例
- 默认放行，坏插件不拖垮全系统的下单能力
- 日志、计数、告警、审计齐全
- 自动停用可手动恢复，不删除绑定与数据

十二、降级策略

12.1 降级的定义

降级 = 在异常情况下，牺牲部分功能，保证核心功能可用。

12.2 降级级别

级别 说明 触发
L0 正常 全部功能 -
L1 轻降级 非核心功能限流 资源紧张
L2 中降级 非核心功能关闭 资源严重不足
L3 重降级 只保留核心功能 系统故障
L4 熔断 停止开仓，只允许平仓 严重异常

12.3 各降级级别的行为

L1 轻降级：

· 日志采样率降低
· 快照频率降低
· 非核心查询限流

L2 中降级：

· 关闭历史数据查询
· 关闭对比功能
· 关闭非关键告警

L3 重降级：

· 只保留订单、持仓、平仓
· 关闭模拟盘
· 关闭审计（保留关键）

L4 熔断：

· 停止所有开仓
· 允许平仓
· 暂停所有实例

12.4 降级的触发

触发条件 降级级别
CPU > 80% 持续 5 分钟 L1
CPU > 90% 持续 5 分钟 L2
内存 > 85% L1
内存 > 95% L2
磁盘 > 90% L1
数据库连接池 > 90% L2
行情全源失败 L3
币安全面不可用 L3
对账差异超阈值 L4

12.5 降级的恢复

· 触发条件消失 → 自动恢复
· 分级恢复（L4 → L3 → L2 → L1 → L0）
· 每次恢复记录审计

12.6 降级的手动控制

· 管理员可手动触发降级
· 管理员可手动恢复
· 记录审计

十三、恢复策略

13.1 恢复的类型

类型 说明
自动恢复 系统自动
半自动恢复 触发特定操作
人工恢复 管理员操作
数据恢复 从备份恢复

13.2 崩溃恢复

触发： 进程重启。

流程：

1. 扫描 enabled=true 的实例
2. 逐个恢复
3. 恢复前对账
4. 失败则状态置 error

限制：

· 并发恢复数：5
· 单实例超时：30 秒
· 总超时：5 分钟

13.3 账号恢复

触发： 用户更新密钥或账号重新有效。

流程：

1. 验证账号
2. 对账
3. 状态恢复
4. 不自动启实例

13.4 连接恢复

触发： 网络恢复。

流程：

1. 重新建立连接
2. 重新订阅
3. 补拉丢失数据

13.5 行情恢复

触发： 行情源恢复。

流程：

1. 重新订阅
2. 更新缓存
3. 恢复 tick 分发

13.6 数据恢复

触发： 数据损坏。

流程：

1. 停止服务
2. 从备份恢复
3. 验证一致性
4. 启动服务

13.7 恢复的统一策略

· 先对账，后恢复
· 不自动重启（避免连环崩）
· 限制并发
· 限制超时
· 失败告警

16.1 重试原则

· 只重试可恢复的异常
· 重试有上限
· 重试有退避
· 重试不改变语义

16.2 重试矩阵

异常 重试 退避 上限

16.3 重试的实现

· 重试逻辑在引擎层
· 重试不改变订单的 client_order_id
· 重试记录日志和指标

16.4 重试的停止条件

· 达到重试上限
· 达到总超时时间
· 异常类型变为不可重试
· 系统进入降级
