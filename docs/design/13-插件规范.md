# 插件规范

> 本文档是 BAMY 框架的第十三份设计文档，定义：插件是什么、与策略的区别、作用域与绑定、钩子与检查点、拦截协议、失败语义、数据范围、plugin.yaml 规范、plugin.py 规范、加载与热更新、安全边界。
> 不写代码，只写规则和逻辑。本文档是完整设计，不是第一版，是最终态。

## 二、插件是什么

### 2.1 定义

**插件**是框架行为的扩展：不决定交易，而是增强框架对交易、对事件、对实例生命周期的处理。

插件 = 一个文件夹 = 一份 `plugin.yaml` + 一份 `plugin.py`（+ 可选辅助文件）。

典型插件：

| 插件 | 做什么 |
|---|---|
| 通知插件 | 把告警、成交、熔断推送到 Telegram / 邮件 / Webhook |
| 风控增强插件 | 自定义规则，在下单前否决不符合条件的订单 |
| 报表插件 | 每日汇总各实例盈亏，生成报表外发 |
| 审计外发插件 | 把审计记录同步到外部日志系统 |
| 对账增强插件 | 对账差异出现时按自定义规则处置 |

### 2.2 插件不是什么

- 插件不是策略。策略产生交易意图，插件改变框架对意图的处理。
- 插件不是实例。插件挂在作用域上，不挂在实例上。
- 插件不是账号。一个插件可以作用于多个账号。
- 插件不是用户。插件属于系统，不属于任何用户。
- **插件不能下单。** 框架不向插件提供任何下单、平仓、撤单接口。这是最硬的一条边界。
- 插件不是万能胶。策略的内部逻辑与插件无关，插件无法读取策略的私有状态。

### 2.3 插件与策略的关系

| | 策略 | 插件 |
|---|---|---|
| 目的 | 决定交易 | 增强框架行为 |
| 载体 | `extensions/strategies/` | `extensions/plugins/` |
| 元信息 | `strategy.yaml` | `plugin.yaml` |
| 代码导出 | `STRATEGY` | `PLUGIN` |
| 挂载点 | 实例 | 作用域（全局 / 用户 / 账号） |
| 配置 | 参数（params） | 设置（settings） |
| 上下文 | StrategyContext | PluginContext |
| 下单能力 | 有 | 无 |
| 生命周期 | on_start / on_tick / on_stop | on_bind / on_unbind / on_settings |
| 变更影响面 | 单个实例 | 整个作用域 |

两者唯一交界：**插件可以在检查点上拦截策略产生的交易意图。**

### 2.4 为什么要有插件

如果一个能力不属于任何具体策略，而是横跨多个策略、多个实例，它就该是插件。三个典型场景：

1. **横切关注点。** 通知推送是所有策略都需要的，但不该在每份策略代码里抄一遍。
2. **管理员管控。** 系统级的规则（如全局禁止某类交易）必须由管理员一次配置、全系统生效，不能依赖用户自觉。
3. **策略不该知道的事。** 策略只表达"我要买"，至于这笔单子要不要被拒绝、要不要被改小，属于框架侧决策。

### 2.5 插件的核心原则

**插件改变框架的行为，但不改变策略的代码。**

- 策略作者不需要知道系统里装了哪些插件
- 插件作者不需要知道系统里跑了哪些策略
- 两者通过框架的检查点解耦

## 三、插件的作用域

### 3.1 三级作用域

| 作用域 | 英文 | 谁能创建绑定 | 影响范围 |
|---|---|---|---|
| 全局 | `global` | 仅管理员 | 全系统所有账号与实例 |
| 用户 | `user` | 用户自己 | 该用户名下全部账号与实例 |
| 账号 | `account` | 用户自己 | 指定一个账号及其下全部实例 |

不设实例级作用域。实例级的精细控制由策略参数或账号级绑定完成。

### 3.2 作用域的选择

插件在 plugin.yaml 里声明自己支持哪些作用域：

```yaml
scopes: [global, account]
default_scope: account
```

- 声明了 `global` 的插件，管理员可以建全局绑定
- 声明了 `account` 的插件，用户可以建账号级绑定
- 声明了 `user` 的插件，用户可以建用户级绑定
- 未声明的作用域，对应入口不显示

### 3.3 绑定

**插件绑定**是插件在某个作用域上的挂载记录：

| 字段 | 说明 |
|---|---|
| id | 绑定 ID |
| plugin_id | 插件 ID |
| plugin_version | 绑定时的插件版本 |
| scope | global / user / account |
| scope_id | 全局为 null；用户为 user_id；账号为 account_id |
| owner_id | 创建者（全局绑定为管理员） |
| enabled | 是否启用 |
| settings | 该绑定上的配置值（对应 plugin.yaml 的 settings schema） |
| priority | 拦截链中的执行顺序，数值小者先执行，默认 100 |
| created_at | 创建时间 |
| updated_at | 更新时间 |

单用户可创建的插件绑定（user 级与 account 级之和）上限默认 20，由系统配置 `plugin.max_per_user` 控制，超限返回 40915。

### 3.4 生效链

同一个插件在一条链路上可能有多份绑定。生效规则：

```
实例 → 取该实例绑定的账号 → 收集该账号上的 account 级绑定
                          → 收集账号归属用户上的 user 级绑定
                          → 收集 global 级绑定（全局唯一一份）
   → 按插件去重：同一插件只生效一次，取优先级最高的一份配置
   → 优先级：account > user > global
```

要点：

- **按插件去重，不按绑定去重。** 同一插件在账号级和全局各有一份绑定时，只生效账号级那份。
- **不同插件各自生效。** 多份绑定互不排斥。
- 去重后，每个生效插件携带一个 `effective_scope`（实际生效的作用域），审计记录里要写清是"哪一级"生效的。
- **模拟盘实例只解析 global 与 user 两级。** 模拟盘实例不绑账号（`account_id` 为空），账号级绑定对模拟盘不生效；框架不为模拟盘设影子账号。详见《模拟盘设计》第十四节。

### 3.5 优先级与拦截链顺序

- `priority` 只在**同一检查点上多个不同插件**之间比较
- 数值小者先执行
- 相同 priority 时，按 `account > user > global` 排，仍相同则按绑定创建时间早者先执行
- 顺序必须在每次执行时重新计算，不得缓存后跨作用域复用

### 3.6 绑定的启停

- 停用一个绑定不删除配置，`enabled = false` 即可，立即生效
- 停用全局绑定同时影响所有未被更高级绑定覆盖的账号
- 插件本体被卸载时，其所有绑定置为 `invalid`

### 3.7 绑定变更的生效时机

| 变更 | 生效时机 |
|---|---|
| 新建 / 启用 / 停用绑定 | 立即 |
| 修改 settings | 立即，且调用 on_settings() |
| 修改 priority | 立即 |
| 删除绑定 | 立即，且调用 on_unbind() |
| 插件重新扫描成功 | 已运行实例下次启动时用新代码 |

## 四、钩子

钩子是插件接入框架的唯一入口，分两类。

### 4.1 订阅型钩子

只接收事件，不改变流程。

| 特征 | 说明 |
|---|---|
| 能否否决 | 否 |
| 能否改数据 | 否 |
| 出错影响 | 只记日志，不影响发布者与其他订阅者 |
| 执行时机 | 事件发布后异步分发 |
| 是否阻塞主流程 | 否 |

订阅的事件类型直接复用事件总线的既有清单，不新增概念：

| 事件 | 说明 |
|---|---|
| `order.created` | 订单已创建 |
| `order.submitted` | 订单已提交交易所 |
| `order.filled` | 订单成交 |
| `order.partial` | 部分成交 |
| `order.failed` | 订单失败 |
| `order.rejected` | 订单被拒 |
| `position.changed` | 持仓变更 |
| `guard.placed` | 保护单已挂 |
| `guard.triggered` | 保护单触发 |
| `guard.missing` | 保护单缺失 |
| `risk.breached` | 风控触发 |
| `risk.circuit_break` | 熔断触发 |
| `risk.circuit_recover` | 熔断解除 |
| `account.invalid` | 账号失效 |
| `account.recovered` | 账号恢复 |
| `account.limit_hit` | 限频触发 |
| `instance.error` | 实例出错 |
| `instance.auto_stopped` | 实例自动停止 |
| `reconcile.diff` | 对账差异 |
| `reconcile.completed` | 对账完成 |
| `system.alert` | 系统告警 |
| `tick` | 行情更新（默认不订阅，需显式声明并限频） |

`tick` 是高频率事件。插件订阅它时必须声明 `throttle`，否则加载失败。

### 4.2 拦截型钩子

挂在框架的关键流程上，可否决或改写。

| 特征 | 说明 |
|---|---|
| 能否否决 | 能 |
| 能否改数据 | 能 |
| 出错影响 | 按 `fail_mode` 处理 |
| 执行时机 | 在流程的检查点上同步执行 |
| 是否阻塞主流程 | 是 |

### 4.3 钩子声明

```yaml
hooks:
  - event: order.filled            # 订阅型
    handler: on_order_filled

  - event: tick                    # 订阅型（高频，必须限频）
    handler: on_tick
    throttle: 5                    # 秒

  - checkpoint: order.before_submit  # 拦截型
    handler: before_order
    fail_mode: open
    timeout_ms: 200
```

### 4.4 钩子的数量限制

- 单个插件最多声明 32 个钩子
- 单个检查点上最多 16 个拦截型钩子，超出时加载报错并提示
- 单个插件最多订阅 16 个事件

## 五、检查点

### 5.1 检查点清单

只设四个检查点，不随意增加。

| 检查点 | 时机 | 典型用途 |
|---|---|---|
| `instance.before_start` | 实例启动前置校验通过后、on_start() 之前 | 拒绝启动、附加启动前动作 |
| `order.before_submit` | 订单中心分段处理中，前置校验通过后、发出请求前 | 拒单、改数量或价格、强制附加保护 |
| `position.before_close` | 平仓动作发出前 | 拒绝平仓（如锁定仓位） |
| `params.before_save` | 实例参数保存前 | 拒绝或修正参数 |

### 5.2 检查点在流程中的位置

```
实例启动：
  用户点启动 → 前置校验 → 【instance.before_start】→ on_start() → 订阅行情 → running

下单：
  策略调 ctx.buy → 前置校验 → 【order.before_submit】→ 发往交易所 → 结果处理
                            （风控也在这一段，风控先于插件）

平仓：
  用户点平仓 / 策略调 close → 权限校验 → 【position.before_close】→ 执行

保存参数：
  用户改参数 → schema 校验 → 【params.before_save】→ 落库
```

### 5.3 与风控的先后

风控中心与插件的顺序固定：**风控先于插件**。

理由：风控是系统自身的硬约束（限额、熔断、回撤），插件是可选增强。风控拒绝的单子不应再经过插件的业务判断，插件的错误也不应影响风控的判断。

## 六、拦截协议

### 6.1 返回值

拦截型钩子的处理函数返回三选一：

| 返回值 | 含义 | 后续 |
|---|---|---|
| `ALLOW` | 放行 | 按原样继续 |
| `DENY(reason)` | 拒绝 | 终止该流程，返回错误码，记审计 |
| `MODIFY(payload)` | 改写 | 用新 payload 继续，可能进入下一个拦截钩子 |

### 6.2 拦截链

同一检查点上的多个插件按 priority 串行执行：

```
输入 payload
  → 插件A（priority 10）→ ALLOW
  → 插件B（priority 20）→ MODIFY  → payload 被替换
  → 插件C（priority 30）→ ALLOW
  → 通过，用改写后的 payload 继续
```

规则：

- 任一插件返回 `DENY`，链条立即终止，后续插件不再执行
- `MODIFY` 后的 payload 传给下一个插件，链上后续插件看到的是最新值
- 链条执行完毕后，最终 payload 才被送出
- 每次拦截的结论都记审计，含插件 ID、绑定 ID、生效作用域、结论、耗时

### 6.3 超时

- 每个拦截钩子有超时，默认 200 毫秒，可在 plugin.yaml 里调，上限 2000 毫秒
- 超时按 `fail_mode` 处理
- 超时计入插件健康统计

### 6.4 各检查点的 payload

| 检查点 | 输入 payload | 可改写的字段 |
|---|---|---|
| `instance.before_start` | `{instance, account, strategy_meta}` | 不可改写，只能放行或拒绝 |
| `order.before_submit` | `{instance, order, symbol, side, amount, price, type}` | amount、price、type |
| `position.before_close` | `{instance, position_id, symbol, amount, is_manual}` | amount |
| `params.before_save` | `{instance, params}` | params 内的值 |

`instance.before_start` 与 `position.before_close` 只支持放行与拒绝，不支持改写。

### 6.5 拒绝后的行为

| 检查点 | 拒绝后的表现 |
|---|---|
| `instance.before_start` | 实例不启动，状态置 `error`，`last_error` 写明被哪个插件拒绝 |
| `order.before_submit` | 下单不发出，订单记为 `rejected`，来源标记为插件拦截 |
| `position.before_close` | 平仓不执行，返回拒绝原因给调用方 |
| `params.before_save` | 参数不落库，返回拒绝原因给用户 |

### 6.6 拒绝的错误码

插件拒绝产生统一错误码，附 `reason` 与 `plugin_id`：

| 错误码 | 含义 |
|---|---|
| `PLUGIN_DENIED` | 被插件拒绝 |
| `PLUGIN_TIMEOUT` | 插件拦截超时且 fail_mode 为拒绝 |
| `PLUGIN_ERROR` | 插件拦截时抛异常且 fail_mode 为拒绝 |

详见《错误码》。

## 七、失败语义

### 7.1 fail_mode

拦截型钩子必须声明 `fail_mode`，决定插件自身异常时怎么办：

| 值 | 含义 | 适用 |
|---|---|---|
| `open`（默认） | 放行，记日志与告警 | 通知类、统计类、非强制的业务规则 |
| `closed` | 拒绝，记审计 | 强制合规类、资金安全类 |

默认 `open`，理由：一个坏掉的插件不应该让全系统下不了单。

### 7.2 失败分类与处理

| 情况 | 订阅型 | 拦截型 |
|---|---|---|
| 处理函数抛异常 | 记日志、计数 | 按 `fail_mode` |
| 处理函数超时 | 记日志、计数 | 按 `fail_mode` |
| 插件模块被卸载 | 停止分发 | 从链条移除 |
| 插件绑定制为 invalid | 停止分发 | 从链条移除 |

### 7.3 插件健康度

框架按插件统计：

| 指标 | 说明 |
|---|---|
| 调用次数 | 订阅型与拦截型分别统计 |
| 异常次数 | 抛错与超时之和 |
| 平均耗时 | 拦截型的关键指标 |
| 最近错误 | 最近一次错误的原文与时间 |

连续异常超过阈值（默认 10 次）时：

- 插件绑定自动置为 `disabled`
- 发布 `system.alert` 事件
- 记审计
- 管理员后台显示为"已自动停用"，并提供手动恢复按钮

### 7.4 失败隔离

- 一个插件失败不影响其他插件
- 插件失败不影响策略的运行
- 插件失败不影响事件总线上其他订阅者

## 八、插件能看到什么

### 8.1 data_scope

插件在 plugin.yaml 里声明数据范围：

| 值 | 含义 | 谁能安装 |
|---|---|---|
| `own` | 只能看到自己绑定所在作用域内的数据 | 管理员与用户 |
| `all` | 能看到全系统的数据 | 仅管理员 |

- 声明 `own` 的插件：账号级绑定时只能收到该账号的事件，用户级绑定时只能收到该用户的事件
- 声明 `all` 的插件：无论挂在哪一级，都能收到全系统事件
- 声明 `all` 的插件，用户不可安装，插件市场里显著标注

### 8.2 数据裁剪

事件分发前按绑定的生效作用域裁剪：

```
事件带 (owner_id, account_id, instance_id)
  → 插件的 data_scope 为 own：
      账号级绑定 → 只发 account_id 匹配的事件
      用户级绑定 → 只发 owner_id 匹配的事件
      全局绑定 → 只发 owner_id 为空的系统事件
  → 插件的 data_scope 为 all：
      不裁剪，全发
```

### 8.3 敏感字段

事件与对象在传给插件前做脱敏：

| 字段 | 处理 |
|---|---|
| 账号密钥 | 从不出现 |
| 账号的 key 明文 | 从不出现 |
| 用户密码 | 从不出现 |
| 插件设置里的 secret 字段 | 只在本插件内可见，其他插件不可见 |
| 其他用户的用户名 | 只在 data_scope 为 all 时可见 |

### 8.4 插件上下文 PluginContext

插件通过 `self.ctx` 访问框架能力：

| 属性/方法 | 说明 |
|---|---|
| ctx.plugin_id | 插件 ID |
| ctx.binding_id | 当前绑定 ID |
| ctx.scope | 生效作用域 |
| ctx.scope_id | 生效作用域的 ID |
| ctx.settings | 该绑定上的设置值 |
| ctx.data_scope | 数据范围 |
| ctx.log / log_info / log_warn / log_error | 写日志 |
| await ctx.state.get(key) | 读绑定级状态 |
| await ctx.state.set(key, value) | 写绑定级状态 |
| await ctx.state.delete(key) | 删绑定级状态 |
| await ctx.notify(title, body, level) | 发系统通知（进通知中心） |
| ctx.http | 受限 HTTP 客户端，只能访问 network.hosts 白名单内的主机；未声明 network 时不可用 |

### 8.5 插件不提供的接口

框架不向插件提供：

- 下单、平仓、撤单、改单的任何方法
- 直接读写数据库的方法
- 直接访问账号密钥的方法
- 直接访问其他插件状态的方法
- 直接调用策略方法的方法

手段上杜绝，不靠约定。

### 9.3 出网声明

插件是唯一允许出网的扩展类型（策略一律禁止）。

- 未声明 `network` → 该插件的网络请求被运行时拦截，抛异常
- 声明了 `enabled: true` 但 `hosts` 为空 → 加载失败
- 只允许访问 `hosts` 白名单内的主机，其他一律拒绝
- 出网失败不影响主流程，按订阅型钩子的异常语义处理

出网是风险面。管理员在安装前应审阅 hosts 列表。

### 9.4 设置 schema

设置（settings）与策略的参数（params）使用**完全相同的类型系统与字段定义**，见《策略规范》第四节与第五节。

用户级与账号级绑定的设置由用户填写；全局绑定的设置由管理员填写。同一插件在不同作用域上的 settings 值互相独立。

## 十、plugin.py 规范

### 10.1 必须实现的内容

```python
from bamy.plugin import BasePlugin, PluginContext, ALLOW, DENY, MODIFY


class TelegramNotify(BasePlugin):
    """插件类，名字随意，但必须继承 BasePlugin"""

    async def on_bind(self):
        """绑定生效时调用一次。"""

    async def on_settings(self):
        """设置变更时调用。"""

    async def on_unbind(self):
        """绑定被删除或停用时调用一次。"""

    async def on_alert(self, event):
        """订阅型钩子的处理函数，名字与 plugin.yaml 的 handler 对应。"""

    async def before_order(self, order):
        """拦截型钩子的处理函数，必须返回 ALLOW / DENY / MODIFY。"""
        return ALLOW


# 必须导出 PLUGIN 变量
PLUGIN = TelegramNotify
```

### 10.2 生命周期方法

| 方法 | 何时调用 | 是否必须 |
|---|---|---|
| on_bind() | 绑定被创建或启用时 | 是 |
| on_settings() | 该绑定的设置被修改时 | 否 |
| on_unbind() | 绑定被删除或停用时 | 是 |

生命周期方法按绑定调用，不是按插件调用。同一插件挂三个作用域，就有三个独立的插件对象，各自收到自己的生命周期回调。

### 10.3 钩子处理函数

| 类型 | 签名 | 返回值 |
|---|---|---|
| 订阅型 | `async def handler(self, event)` | 无返回值，返回值被忽略 |
| 拦截型 | `async def handler(self, payload)` | `ALLOW` / `DENY(reason)` / `MODIFY(payload)` |

规则：

- 名字必须与 plugin.yaml 的 `handler` 字段一致
- 必须是 async 函数
- 拦截型必须返回三种结论之一，返回其他值按 `PLUGIN_ERROR` 处理
- 同一绑定的处理函数串行执行，不会并发

### 10.4 异常处理

- 钩子处理函数抛出的异常由框架捕获
- 订阅型：记日志、计数，不影响发布者
- 拦截型：按 `fail_mode` 处理
- 生命周期方法抛异常：记日志、计数，不阻断绑定的建立或解除
- 连续异常超阈值 → 绑定自动停用，见第七节

### 10.5 异步要求

- 所有方法与钩子处理函数必须是 async 函数
- 拦截型钩子运行在关键路径上，任何阻塞操作都会拖慢下单
- 框架保证同一绑定内的方法调用是串行的
- 框架保证同一检查点上的插件按优先级串行执行，不并发

## 十一、插件安全边界

### 11.1 沙箱目标

插件的代码不能：

- 访问文件系统（除插件自己的目录）
- 访问数据库
- 访问环境变量
- 访问其他绑定或插件的状态
- 访问账号密钥
- 下单、平仓、撤单
- 使用 subprocess / eval / exec / compile
- 修改框架内部状态

与策略的差异只有一条：**插件在声明了 `network` 的前提下可以出网，且只能访问白名单主机。**

### 11.2 沙箱实现思路

- 只能 import 白名单内的模块
- 出网必须走框架提供的 HTTP 客户端（受白名单与超时约束）
- 数据库访问必须走 ctx.state
- AST 静态检查 + 运行时拦截双重防护

### 11.3 白名单模块

插件可以 import：

- 标准库（不含 os、sys、subprocess、socket 等危险模块）
- 声明在 dependencies 里的第三方库
- bamy.plugin（框架提供的基类和上下文）
- 插件自己 helpers/ 下的模块

### 11.4 危险操作拦截

| 操作 | 处理 |
|---|---|
| import os | 拒绝加载 |
| import subprocess | 拒绝加载 |
| import socket | 拒绝加载 |
| import ccxt | 拒绝加载 |
| open(...) 写文件（插件目录外） | 运行时拦截 |
| eval(...) / exec(...) | 拒绝加载 |
| 访问 ctx._internal | 运行时拦截 |
| 未声明 hosts 的出网 | 运行时拦截 |
| 调用任何下单相关方法 | 方法不存在，直接报错 |

### 11.5 沙箱的定位

沙箱只防误操作，不防恶意代码：

- 防止插件无意中破坏框架、越过上下文直接访问资源
- 插件上下文不提供下单接口，插件无法通过框架 API 越权交易
- 插件与框架运行在同一进程内，不做子进程或容器隔离
- 只安装可信来源的插件包；安装即视为管理员对代码负责
- AST 静态检查与运行时拦截可被刻意绕过，不能作为对抗恶意代码的安全边界

## 十二、插件与框架的接口契约

### 12.1 框架承诺给插件

- 稳定的 BasePlugin 基类
- 稳定的 PluginContext 接口
- 稳定的钩子注册与调用方式
- 稳定的检查点位置与 payload 结构
- 稳定的拦截结论协议
- 稳定的设置传入方式
- 稳定的日志与状态存储接口

### 12.2 插件承诺给框架

- 实现必须的生命周期方法
- 实现声明的全部钩子处理函数
- 拦截型钩子返回合法结论，且在自己的超时内返回
- 不访问框架禁止的资源
- 设置只从 ctx.settings 读
- 出网只访问声明的主机
- 日志只用 ctx.log

### 12.3 契约变更

- 框架升级若改变契约，必须提升主版本号
- 新增检查点属于次版本变更，但插件不得假定检查点数量固定
- 插件通过 min_bamy_version 声明兼容性
- 不兼容的旧插件明确拒绝加载并提示

from bamy.plugin import BasePlugin


class TelegramNotify(BasePlugin):

    async def on_bind(self):
        self.ctx.log(f"绑定生效，作用域 {self.ctx.scope}")

    async def on_settings(self):
        await self._send("设置已更新")

    async def on_unbind(self):
        self.ctx.log("绑定已解除")

    async def on_alert(self, event):
        await self._send(f"[告警] {event['message']}")

    async def on_circuit_break(self, event):
        await self._send(f"[熔断] 账号 {event['account_id']} 已熔断")

    async def on_auto_stopped(self, event):
        await self._send(f"[实例停止] {event['instance_name']}")

    async def _send(self, text):
        token = self.ctx.settings["bot_token"]
        chat = self.ctx.settings["chat_id"]
        await self.ctx.http.post(
            f"https://api.telegram.org/bot{token}/sendMessage",
            json={"chat_id": chat, "text": text},
        )


PLUGIN = TelegramNotify

## 十四、插件失败处理

### 14.1 加载失败

| 原因 | 处理 |
|---|---|
| plugin.yaml 缺失 | 记录失败，跳过 |
| plugin.yaml 格式错 | 记录失败，跳过 |
| plugin.py 缺失 | 记录失败，跳过 |
| plugin.py 语法错 | 记录失败，跳过 |
| PLUGIN 变量缺失 | 记录失败，跳过 |
| PLUGIN 不是类 | 记录失败，跳过 |
| PLUGIN 未继承 BasePlugin | 记录失败，跳过 |
| kind 不是 plugin | 记录失败，跳过 |
| scopes 为空或含未知值 | 记录失败，跳过 |
| data_scope 非法 | 记录失败，跳过 |
| 钩子声明了未实现的方法 | 记录失败，跳过 |
| 拦截型钩子未声明 fail_mode | 使用默认 open，记警告 |
| 订阅 tick 未声明 throttle | 记录失败，跳过 |
| network.enabled 为 true 但 hosts 为空 | 记录失败，跳过 |
| 检查点上拦截插件超过上限 | 记录失败，跳过 |
| 未知设置类型 | 记录警告，设置项跳过 |

任何失败都不影响其他插件加载。

### 14.2 运行时失败

| 情况 | 处理 |
|---|---|
| 订阅型钩子抛异常 | 记日志、计数，不影响其他订阅者 |
| 拦截型钩子抛异常 | 按 fail_mode |
| 拦截型钩子超时 | 按 fail_mode |
| 出网失败 | 记日志、计数 |
| 生命周期方法抛异常 | 记日志、计数，不阻断绑定操作 |
| 连续异常超阈值 | 绑定自动停用，发告警，记审计 |

### 14.3 失败通知

- 加载失败：管理员后台可见
- 运行时失败：绑定所属的用户或管理员可见
- 自动停用：发 `system.alert`，管理员后台可见

### 14.4 失败恢复

- 加载失败：修复插件文件后，手动触发重新扫描
- 运行时失败：修复后，手动恢复绑定
- 绑定被自动停用：管理员可在插件管理页手动恢复，恢复后健康计数归零

## 十五、插件的加载、热更新与卸载

### 15.1 加载

```
启动 → 扫描 extensions/plugins/ → 读 plugin.yaml → 导入 plugin.py
     → 校验钩子与实现 → 注册插件 → 完成
```

### 15.2 绑定解析

绑定的解析在实例启动时与绑定发生变更时各做一次：

```
收集候选绑定（account / user / global）
  → 过滤 enabled = false
  → 过滤插件未加载成功
  → 按插件去重，取最高优先级作用域
  → 按 priority 排序
  → 得到生效插件列表与拦截链
```

### 15.3 热更新

1. 管理员点击"重新扫描扩展"
2. 框架重新扫描 `extensions/plugins/` 目录
3. 对已存在的插件：文件有变化则重新加载，无变化则跳过
4. 对新插件：加载并注册，但不自动创建绑定
5. 对消失的插件：所有相关绑定置为 `invalid`，从生效列表移除
6. 正在运行的实例：已生效的拦截链保持原代码运行，不中断
7. 加载失败：保留旧版本，记录失败原因

### 15.4 热更新的限制

- 不能热更新已生效绑定的代码（模块重载有风险）
- 只保证"下次绑定解析时用新代码"
- 若插件新增了 dependencies，需要重启服务
- 若插件的 settings schema 有破坏性变更，已有绑定需人工确认

### 15.5 卸载

```
管理员卸载插件 → 解绑所有绑定（置 invalid）
             → 从生效列表移除
             → 卸载模块、清理缓存
```

插件卸载不需要停止实例，也不影响策略的运行。
