BAMY 用户与权限设计

本文档定义 BAMY 的用户体系与权限体系：用户从哪来、怎么登录、有哪些角色、能看什么、能做什么、数据归谁、如何隔离、如何审计、如何分享。
不写代码，只写规则和逻辑。本文档是完整设计，不是第一版，是最终态。

一、文档要回答的问题

1. 用户怎么产生
2. 用户怎么进入系统
3. 系统里有哪些角色和权限
4. 每个角色能看到什么
5. 每个角色能做什么
6. 数据归谁、怎么隔离
7. 用户状态如何变化
8. 所有关键行为如何留痕
9. 访客如何只读访问
10. 安全底线是什么

二、用户从哪来

2.1 注册方式

系统支持三种注册入口：

方式 说明 开启开关
用户名 + 密码 默认开启 ALLOW_REGISTER
邮箱 + 密码 需要邮箱验证 ALLOW_EMAIL_REGISTER
邀请码 + 用户名 + 密码 只有持邀请码的人能注册 ALLOW_INVITE_REGISTER

三种方式不互斥，可以同时开启，用户注册时可选。

2.2 注册字段

字段 必填 规则
用户名 是 4-32 字符，字母数字下划线，全局唯一
密码 是 8-64 字符，至少包含字母和数字，可配置强度
邮箱 选填（开启邮箱注册时必填） 标准邮箱格式，唯一
邀请码 选填（开启邀请注册时必填） 由管理员或系统生成
昵称 选填 显示名，可重复

2.3 密码规则

· 长度 8-64
· 至少包含字母和数字
· 不允许纯数字、纯字母
· 不允许与用户名相同
· 不允许常见弱密码（内置一份弱密码字典）
· 存储：bcrypt 哈希，cost 因子可配（默认 12）
· 永不明文存储，永不回显

2.4 邮箱验证

如果开启邮箱注册：

1. 用户提交邮箱
2. 系统发验证邮件（带一次性 token）
3. 用户点链接验证
4. 验证通过才算注册完成
5. token 有效期 30 分钟
6. 未验证的账号状态为 pending，不能登录

2.5 邀请码

· 邀请码由管理员生成
· 每个邀请码可以设置：使用次数上限、过期时间、绑定的角色
· 邀请码使用后记录“被谁用了”
· 邀请码可以手动禁用

2.6 注册限制

限制 规则
同一 IP 每小时注册次数 默认 5 次，可配
同一邮箱注册次数 1 次
同一用户名 全局唯一
注册频率超限 返回“请稍后再试”，并记录审计
注册是否需审核 可配置：直接通过 / 管理员审核

2.7 管理员从哪来

管理员不开放注册。 产生方式：

1. 系统初始化时，通过 /api/setup 创建第一个管理员（仅当系统无任何用户时可用）
2. 现有管理员在后台指定其他用户为管理员
3. 通过环境变量指定初始管理员（首次启动时创建）

2.8 第一个管理员

首次启动时：

· 若数据库无任何用户 → /api/setup 可访问，创建一个初始管理员
· 若已有用户 → /api/setup 永久关闭，返回 404

这样既保证有入口，又不会留下后门。同时允许通过环境变量 INIT_ADMIN_USER 和 INIT_ADMIN_PASS 自动创建初始管理员。

三、用户如何进入系统

3.1 登录方式

系统支持多种登录方式：

方式 说明
用户名 + 密码 基础方式
邮箱 + 密码 如果注册时绑定了邮箱
API Token 用于程序化访问，用户在后台生成
第三方 OAuth 可扩展（Google / GitHub），通过开关控制

3.2 登录流程

1. 用户提交凭证
2. 系统校验
3. 通过 → 签发 JWT + Refresh Token
4. 前端存 JWT（内存）+ Refresh Token（httpOnly cookie 或 localStorage）

3.3 JWT 设计

项目 值
算法 HS256
有效期 默认 30 分钟，可配
载荷 user_id、role、jti（唯一 ID）、iat、exp
密钥 环境变量，不硬编码
是否可撤销 是（通过 jti 黑名单）

3.4 Refresh Token

项目 值
有效期 默认 7 天，可配
存储 服务端存哈希，客户端存原值
使用方式 换新的 JWT + 新的 Refresh Token（轮换）
撤销 支持主动撤销（登出、改密、禁用用户时）
一用户可有几个 可配（默认 5 个设备）

每次刷新时旧 Refresh Token 立即失效，防止重放。

3.5 登出

登出分两种：

类型 行为
单设备登出 撤销当前 Refresh Token，当前 JWT 加入黑名单
全设备登出 撤销该用户所有 Refresh Token，所有 JWT 失效

3.6 登录失败处理

情况 处理
用户名/邮箱不存在 返回“用户名或密码错误”（不暴露哪个错）
密码错误 同上
用户状态非 active 返回具体原因（pending/disabled/locked）
连续失败 N 次 锁定账号 15 分钟（N 可配，默认 5）
锁定期间登录 返回“账号已锁定，请稍后再试”
IP 频繁失败 该 IP 限流

3.7 修改密码

· 需要验证旧密码
· 修改后：
  · 撤销所有其他设备的 Refresh Token
  · 当前设备保留
  · 记审计
· 密码强度规则同注册

3.8 找回密码

· 通过绑定邮箱找回
· 发一次性重置 token（有效期 30 分钟）
· 重置后撤销所有会话
· 无邮箱的用户只能联系管理员重置

3.9 两步验证（2FA）

可选功能，通过开关控制：

· 支持 TOTP（Google Authenticator 等）
· 用户主动开启后，登录需要输入 6 位动态码
· 提供恢复码（一次性使用，10 个）
· 管理员可以强制某用户开启 2FA

四、角色与权限

4.1 角色列表

角色 说明
guest 未登录访客，仅可访问分享链接
user 普通用户，看自己的数据
admin 管理员，看所有人的数据
super_admin 超级管理员，拥有所有权限

四种角色，逐级递进。

注册/登录 ✗ ✓ ✓ ✓
管理自己账号 ✗ ✓ ✓ ✓
管理自己实例 ✗ ✓ ✓ ✓
查看自己数据 ✗ ✓ ✓ ✓
查看所有用户 ✗ ✗ ✓ ✓
查看所有账号 ✗ ✗ ✓ ✓
查看所有实例 ✗ ✗ ✓ ✓
强停任意实例 ✗ ✗ ✓ ✓
禁用/启用用户 ✗ ✗ ✓ ✓
指定/取消管理员 ✗ ✗ ✗ ✓
修改系统配置 ✗ ✗ ✗ ✓
触发插件热加载 ✗ ✗ ✓ ✓
解除账号级熔断 ✗ ✗ ✓ ✓
解除全局熔断 ✗ ✗ ✗ ✓
查看审计日志（自己） ✗ ✓ ✓ ✓
查看审计日志（全部） ✗ ✗ ✓ ✓
硬删除用户 ✗ ✗ ✗ ✓

4.3 权限的判定方式

权限判定采用固定角色制：四种角色的能力由 4.2 的矩阵唯一确定，系统不存在第五种角色，也不存在角色之外的能力来源。

判定规则：

· 每个接口在定义时标注所需的最低角色
· 请求到达时，比较调用者角色与接口要求的最低角色，不满足即拒绝
· 角色等级为 guest < user < admin < super_admin，高等级自动具备低等级的全部能力
· 数据范围与能力同时判定：能力决定"能不能做"，数据范围决定"对谁做"

角色到接口的映射：

| 接口类别 | 最低角色 |
|---|---|
| 分享链接只读访问 | guest |
| 自己的账号、实例、订单、持仓、日志 | user |
| 全站查看、禁用启用用户、强停实例、触发插件热加载、解除账号级熔断 | admin |
| 角色变更、系统配置、硬删除用户、解除全局熔断 | super_admin |

设计约束：

· 角色与能力的对应关系是数据，不是代码分支；新增接口只增加一条映射
· 判定在接口层统一收口，服务层不再重复判断角色
· 权限不足返回 40301 或 40302；访问他人资源时返回 404 伪装，避免通过错误差异枚举资源
· 角色变更不改变历史数据归属，只影响后续请求的判定结果

4.4 角色如何变更

· user → admin：由 super_admin 指定
· admin → super_admin：由 super_admin 指定
· 任何角色 → user：由 super_admin 取消
· 不能取消自己的 super_admin
· 系统至少保留一个 super_admin，不能全部取消

4.5 角色变更的连带动作

· 记录审计（谁改的、什么时候、改的谁、从什么到什么）
· 角色变更不撤销当前会话，下次签发 JWT 时用新角色
· 如果是降级（如 admin → user），建议主动撤销该用户所有会话，避免旧 JWT 的旧权限生效

七、数据归谁，如何隔离

7.1 数据归属原则

所有业务数据都必须带 owner_id。

数据 是否带 owner_id 说明
账号 是 
实例 是 
订单 是 冗余存储，便于查询
持仓 是 同上
日志 是 
快照 是 
审计记录 是 
分享 token 是 
API Token 是 
Refresh Token 是 

全局共享数据（不带 owner_id）：

· 插件元信息
· 系统配置
· 邀请码（由系统所有）
· 全局熔断记录

7.2 隔离规则

普通用户的任何查询，强制加 WHERE owner_id = 当前用户。

这条规则在服务层统一执行，不在每个接口里手写。

具体实现：

· 用户端接口走 /api/...
· 服务层有“当前用户上下文”（从 JWT 中提取）
· 所有数据访问自动带上 owner 过滤
· 管理员接口走 /api/admin/...，用另一套不带过滤的服务调用

不允许在同一个接口里通过 if 是管理员 判断来切换过滤逻辑。物理分离。

7.3 越权访问的处理

如果用户 A 尝试访问用户 B 的实例（比如手动改 URL 里的 ID）：

· 后端查库时带上 owner 过滤 → 查不到 → 返回 404
· 不返回 403，避免暴露“这条数据存在但不是你的”
· 同时记一条审计日志（“疑似越权访问”）
· 连续越权访问触发告警

7.4 用户被禁用后的数据

· 数据不删
· 用户的实例全部停止（由系统触发）
· 用户不能登录，但数据保留
· 管理员可以恢复用户，恢复后数据还在
· 分享 token 全部撤销

7.5 用户被硬删除

只有 super_admin 可以硬删除用户。

硬删除流程：

1. 先禁用用户（自动）
2. 停止所有实例
3. 清空所有持仓（可选：拒绝删除，要求用户先平仓）
4. 二次确认（输入用户名）
5. 记录审计
6. 级联删除：账号、实例、订单、持仓、日志、快照、token

硬删除不可恢复。 建议在实际操作前先导出数据备份。

7.6 数据导出

· user 可导出自己的数据（账号、实例、订单、日志）
· admin 可导出指定用户的数据
· super_admin 可导出全部数据
· 导出格式：JSON / CSV
· 导出时自动脱敏：API secret 不导出，密码不导出

八、用户状态变化

8.1 状态列表

状态 说明
pending 待验证（邮箱未验证，或待管理员审核）
active 正常
disabled 被管理员禁用
locked 因登录失败被临时锁定
deleted 已软删除（数据保留，不可登录）

8.2 状态变化规则

从 到 触发者 附加动作
—— pending 注册 发验证邮件
pending active 用户验证邮箱 / 管理员审核 允许登录
active disabled admin/super_admin 停所有实例、撤销所有会话、撤销所有分享 token
disabled active admin/super_admin 不自动恢复实例，让用户手动启
active locked 系统 登录失败 N 次后
locked active 系统 / 管理员 15 分钟后自动解锁，或管理员手动
active deleted super_admin 软删除（数据保留）
deleted active super_admin 恢复

8.3 状态变化的影响

状态 能否登录 已有会话 实例是否运行 分享 token
pending 否 无 无 无
active 是 有效 正常运行 有效
disabled 否 全部撤销 全部停止 全部撤销
locked 否（临时） 有效 正常运行 有效
deleted 否 全部撤销 全部停止 全部撤销

九、访客与分享 token

9.1 分享 token 是什么

用户可以为自己某个实例生成一个只读分享 token，把这个 token 给任何人，对方无需登录就能看这个实例的概览。

9.2 与登录 JWT 的区别

项目 登录 JWT 分享 token
用途 进入后台 只看一个盘
权限 用户权限 只读，只看一个实例
有效期 30 分钟 用户自定（最长 90 天）
能否撤销 过期即失效 可以主动撤销
能否操作 能 绝对不能
一个用户能有几个 同时 1 个 可以多个
是否带用户信息 是 否

这是两套东西，绝不混用。

9.3 分享 token 的生成

· 用户在实例详情页点击“生成分享链接”
· 选择有效期（1 天 / 7 天 / 30 天 / 90 天 / 自定义）
· 选择显示内容（净值 / 持仓 / 订单 / 参数 / 日志）
· 生成后返回一个 URL
· 用户可复制、可撤销

9.4 分享 token 能看到什么

用户生成时可以勾选显示哪些内容：

内容 默认 可关闭
净值 / 收益率 显示 是
持仓 显示 是
订单列表 显示 是
参数（只读） 隐藏 是
日志 隐藏 是
实例名 显示 否
策略名 显示 否
交易对 显示 否

无论勾选什么，都看不到：

· 账号信息
· 用户信息
· 其他实例
· 任何可操作按钮

9.5 分享 token 的撤销

· 用户可以随时撤销某个分享 token
· 撤销后立即失效
· 用户可以看到自己生成了哪些分享 token、什么时候生成的、最后访问时间、访问次数

9.6 分享 token 的安全限制

· 每个分享 token 绑定一个实例
· 一旦实例被删除，所有相关分享 token 立即失效
· 一旦用户被禁用，所有分享 token 立即失效
· 分享 token 不能用于任何写操作
· 分享 token 有独立的访问日志（谁访问了、什么时候、IP）

十、所有关键行为如何留痕

10.1 审计范围

以下行为必须写审计日志：

行为 记录内容
注册 谁、什么时候、IP、注册方式
邮箱验证 谁、什么时候
登录成功 谁、什么时候、IP、设备
登录失败 用户名、什么时候、IP、原因
登出 谁、什么时候、设备
修改密码 谁、什么时候
重置密码 谁发起的、重置的是谁
2FA 开启/关闭 谁、什么时候
生成/撤销 API Token 谁、什么时候、哪个 token
创建/删除账号 谁、对哪个账号
创建/启停/删除实例 谁、对哪个实例
修改实例参数 谁、哪个实例、旧值、新值
换插件 谁、哪个实例、旧插件、新插件

手动开仓 同上
熔断触发 哪个账号/全局、原因、触发者
熔断解除 谁解除的、什么时候
对账差异修正 哪个实例、差异内容、修正结果

系统配置修改 谁、改了什么

10.2 审计日志的字段

字段 说明
id 主键
timestamp 时间（精确到毫秒）
actor_id 操作人 ID（系统触发为 0）
actor_role 操作人角色
action 操作类型
target_type 目标类型（user / account / instance / order / …）
target_id 目标 ID
old_value 旧值（JSON，如适用）
new_value 新值（JSON，如适用）
result 成功 / 失败
fail_reason 失败原因
ip 操作来源 IP
user_agent 操作来源 UA
request_id 请求唯一 ID（用于串联）
source 触发来源：strategy / manual / guard / system / admin

10.3 审计日志的访问

· 普通用户：只能看与自己相关的审计日志
· admin：能看所有人的
· super_admin：能看所有人的 + 系统级
· 审计日志不可修改、不可删除
· 审计日志保留时间：永久（可配置归档策略）

10.4 触发来源

审计记录必须区分来源：

来源 说明
strategy 策略代码触发（策略自己下单）
manual 用户手动点击触发
guard 保护机制触发（保护单被强平）
system 系统自动触发（熔断、对账修正）
admin 管理员操作
api 通过 API Token 调用触发

这样查历史时能分清“这单是策略下的还是人下的”。

10.5 审计日志的存储

· 存在独立表 audit_logs
· 按时间分区（如按月分表，或按年归档）
· 索引：actor_id、target_id、timestamp、action
· 定期归档：超过 N 年的记录移到冷存储

十一、接口的鉴权规则

11.1 五类接口

前缀 鉴权 数据范围
/api/auth/* 无 注册/登录/找回密码
/api/setup 无 仅首次初始化可用
/api/* 登录 JWT 强制 owner_id = 当前用户
/api/admin/* 登录 JWT + 角色≥admin 全局，不过滤
/api/super/* 登录 JWT + 角色=super_admin 全局 + 系统级

11.2 访客接口

前缀 鉴权 数据范围
/view/{token} 分享 token 只读，只限该 token 绑定的实例

11.3 WebSocket 接口

路径 鉴权 用途
/ws/user 登录 JWT 推送自己的实例事件
/ws/admin 登录 JWT + 角色≥admin 推送全局事件
/ws/view/{token} 分享 token 推送该实例的公开事件

11.4 鉴权失败统一返回

情况 HTTP 状态
未登录 / token 无效 401
已登录但角色不足 403
已登录但目标不存在（或被隔离） 404（不返回 403，防信息泄露）
分享 token 无效 / 过期 401
频率超限 429
服务器错误 500

11.5 限流规则

接口 限制
/api/auth/login 每 IP 每分钟 10 次
/api/auth/register 每 IP 每小时 5 次
/api/auth/forgot 每邮箱每小时 3 次
其他 /api/* 每用户每分钟 120 次
/api/admin/* 每管理员每分钟 300 次
/view/{token} 每 token 每分钟 60 次

十二、安全底线（不可协商）

1. API secret 永不明文回显，任何角色都不行
2. 密码永不明文存储，bcrypt 哈希
3. 密码永不明文回显，任何角色都不行
4. 登录失败统一提示，不区分“用户名不存在”和“密码错误”
5. 越权访问返回 404，不返回 403
6. 管理员不能查看用户密钥明文
7. 分享 token 绝对只读
8. 审计日志不可篡改
9. super_admin 不能取消自己（若只剩一个）
10. 系统至少保留一个 super_admin
11. 所有敏感操作必须记审计
12. JWT 密钥不能硬编码在代码里，必须从环境变量读
13. Refresh Token 必须哈希存储
14. API Token 必须哈希存储
15. 硬删除必须二次确认 + 记审计
16. 数据导出必须自动脱敏
17. 所有密码学操作使用标准库，不自己造轮子
18. HTTPS 强制（生产环境）
19. CORS 白名单，不允许 *（生产环境）
20. Cookie 使用 httpOnly + Secure + SameSite=Lax

十三、API Token（程序化访问）

13.1 用途

用户生成 API Token，用于：

· 脚本访问自己的数据
· 第三方工具集成
· 自动化任务

13.2 生成

· 用户在后台生成
· 生成时设置：
  · 名称（用于区分）
  · 权限范围（只读 / 读写）
  · 有效期（可永久）
· 生成后返回 token 原值仅一次，之后只显示前缀

13.3 使用

· 请求头：Authorization: Bearer <api_token>
· 服务端验证：查哈希 → 匹配 → 提取用户 → 按权限范围执行

13.4 权限范围

范围 说明
read 只读自己的数据
write 读写自己的数据（不含账号密钥、密码）
admin 只 super_admin 可生成，等同管理员

13.5 撤销

· 用户可随时撤销自己的 API Token
· 撤销后立即失效
· 用户可查看所有 token 的最后使用时间、使用次数

十四、安全事件响应

14.1 可疑行为检测

系统自动检测以下行为并记录：

· 连续登录失败（同一用户、同一 IP）
· 短时间大量越权访问
· 短时间大量数据导出
· 异常地理位置登录（如果做 IP 地理库）
· 异常时段登录（凌晨频繁操作）

14.2 自动响应

事件 响应
连续登录失败 N 次 锁定账号 15 分钟
同 IP 大量失败 封禁该 IP 1 小时
大量越权访问 临时禁用该用户，通知管理员
大量数据导出 暂停导出，通知管理员

14.3 通知管理员

· 通过后台通知中心
· 通过邮件（可配）
· 通过 Webhook（可配）

14.4 事件记录

所有安全事件写入审计表，附带“是否已处理”“谁处理的”。
